## La idea

**TCP** es un protocolo que da a dos programas un **canal fiable de bytes**: lo que uno escribe llega al otro, en orden y sin huecos. Un servidor TCP funciona en tres pasos:

1. `TcpListener::bind(dirección)` reserva un **puerto** (un número de 0 a 65535) en una dirección IP.
2. `listener.incoming()` (o `accept()`) espera a que alguien se conecte y entrega un `TcpStream` por cada conexión.
3. Con el `TcpStream`, que implementa `Read` y `Write`, conversas: lees con `BufReader` y respondes con `write!`. Cuando el `TcpStream` se destruye, la conexión se cierra (RAII otra vez).

El cliente usa `TcpStream::connect("127.0.0.1:7878")` y obtiene el mismo tipo de canal. Todo lo de las lecciones 2 y 3 sobre leer y escribir vale tal cual: un socket es «otro sitio que implementa `Read` y `Write`».

## Pruébalo

Este es el servidor de eco (está en `ejemplos/m22/servidor-eco.rs`; verificado que compila con `rustc --emit=metadata`). Devuelve cada línea en mayúsculas:

```rust
use std::io::{BufRead, BufReader, Write};
use std::net::{TcpListener, TcpStream};

fn atender(flujo: TcpStream) -> std::io::Result<()> {
    let quien = flujo.peer_addr()?;
    println!("conexión de {quien}");
    let mut escritor = flujo.try_clone()?;
    for linea in BufReader::new(flujo).lines() {
        let linea = linea?;
        writeln!(escritor, "{}", linea.to_uppercase())?;
    }
    println!("{quien} se fue");
    Ok(())
}

fn main() -> std::io::Result<()> {
    let oyente = TcpListener::bind("127.0.0.1:7878")?;
    println!("escuchando en {}", oyente.local_addr()?);
    for flujo in oyente.incoming() {
        if let Err(e) = atender(flujo?) {
            eprintln!("error con un cliente: {e}");
        }
    }
    Ok(())
}
```

En tu PC: `cargo run` en una terminal y, en otra, conéctate con un cliente TCP. En PowerShell puedes escribir un cliente de diez líneas en Rust con `TcpStream::connect`, o usar `telnet 127.0.0.1 7878` si lo tienes activado. Salida típica en el servidor: una línea `escuchando en 127.0.0.1:7878` y, por cada cliente, `conexión de 127.0.0.1:<puerto del cliente>`.

En el navegador, `TcpListener::bind` devuelve el error `operation not supported on this platform` (lo comprobamos con el runtime WASI del curso).

## Bajo el capó

<BajoElCapo>

**Un socket es un descriptor.** Igual que un `File`, un `TcpListener` y un `TcpStream` guardan el número que el sistema operativo usa para ese canal. `bind`, `listen`, `accept`, `connect`, `read` y `write` son llamadas al sistema; la biblioteca estándar las envuelve en tipos seguros cuyo `Drop` cierra el socket.

**`try_clone`.** El servidor necesita leer y escribir a la vez sobre el mismo socket, pero `BufReader::new(flujo)` **toma propiedad** del `TcpStream`. `try_clone` pide al sistema un **segundo descriptor** para el mismo socket: uno se usa para leer y el otro para escribir, sin pelearse con el borrow checker.

**Bloqueante.** `accept` y `read` **paran el hilo** hasta que pasa algo. Por eso este servidor atiende a un cliente detrás de otro. Las soluciones:

- **Un hilo por cliente**: `std::thread::spawn(move || atender(flujo))`. El `move` traslada la propiedad del `TcpStream` al hilo; `TcpStream` es `Send`, así que el compilador lo permite. Sencillo, pero cada hilo cuesta memoria (su pila).
- **Async** (mundo 18): un runtime como Tokio usa llamadas no bloqueantes del sistema (epoll en Linux, IOCP en Windows) para atender miles de conexiones con pocos hilos.

</BajoElCapo>
