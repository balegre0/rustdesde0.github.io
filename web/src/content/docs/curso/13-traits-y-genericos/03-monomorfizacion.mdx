## La idea

Escribes `fn doble<T>(x: T) -> T` una vez. Pero el procesador no sabe qué es un «`T`»: sumar dos `i32` es una instrucción y sumar dos `f64` es otra muy distinta. Así que el compilador hace lo único posible: **mira todas las llamadas** y, por cada tipo distinto que encuentra, escribe una copia de la función con `T` sustituido. Este proceso se llama **monomorfización** (*monomorphization*: «hacer de una sola forma»).

El resultado tiene dos caras. **Lo que ganas**: cada copia es tan rápida como si la hubieras escrito a mano para ese tipo; no hay ninguna decisión «¿qué tipo era?» al ejecutar, y el compilador puede incluso pegar el cuerpo dentro de quien la llama (*inlining*). **Lo que pagas**: el ejecutable crece con cada tipo usado y la compilación tarda más, porque hay más código que generar y optimizar.

Llamar diez veces con `i32` **no** crea diez copias: crea una y la reutiliza. El coste crece con el número de **tipos distintos**, no de llamadas.

## Bajo el capó

<BajoElCapo>

Este es el ensamblador real de dos usos de una función genérica (x86-64, Windows, `rustc 1.99.1 -O`). El fuente:

```rust
#[inline(never)]
fn doble<T: Add<Output = T> + Copy>(x: T) -> T { x + x }
#[unsafe(no_mangle)] pub fn usa_i32(a: i32) -> i32 { doble(a) }
#[unsafe(no_mangle)] pub fn usa_f64(b: f64) -> f64 { doble(b) }
```

Y lo que sale (quitando directivas):

```text
_RINvCsQRxP6z4OUx_4mono5dobledEB2_:      ; doble::<f64>
	addsd	xmm0, xmm0                       ; suma de decimales (registro xmm)
	ret

_RINvCsQRxP6z4OUx_4mono5doblelEB2_:      ; doble::<i32>
	lea	eax, [rcx + rcx]                   ; suma de enteros
	ret

usa_f64:
	jmp	_RINvCsQRxP6z4OUx_4mono5dobledEB2_
usa_i32:
	jmp	_RINvCsQRxP6z4OUx_4mono5doblelEB2_
```

Hay **dos funciones `doble`** con nombres distintos. El nombre «destrozado» (*mangled*) codifica el tipo: la `d` antes de `EB2_` significa `f64` y la `l` significa `i32`. Cada copia usa instrucciones distintas: `addsd` trabaja con registros de coma flotante y `lea eax, [rcx + rcx]` es un truco para sumar un entero consigo mismo. No queda ni rastro de «`T`».

Si quitas `#[inline(never)]`, el optimizador hace algo aún mejor: pega la suma directamente dentro de `usa_i32` y `usa_f64`, y la función `doble` desaparece. Eso solo es posible porque la llamada es directa a una copia concreta.

Hay técnicas para reducir el coste en tamaño cuando una función genérica es grande: mover la parte que no depende de `T` a una función interna normal, que existe una sola vez. En la lección 5 verás la alternativa opuesta: `dyn Trait`, una sola copia que decide al ejecutar.

</BajoElCapo>

## Trampa típica

<Trampa titulo="«Los genéricos son lentos porque comprueban el tipo al ejecutar»">

Es al revés. Los genéricos se resuelven **al compilar**: el programa terminado no sabe que hubo un genérico. Lo que sí puede crecer es el **tamaño** del ejecutable y el **tiempo de compilación**, si usas una función genérica grande con muchísimos tipos.

</Trampa>
