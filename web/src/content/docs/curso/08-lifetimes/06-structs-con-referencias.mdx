Un **struct** agrupa varios valores con nombre en un tipo nuevo: `struct Punto { x: i32, y: i32 }`, y se crea con `Punto { x: 1, y: 2 }`. Lo estudiarás a fondo en el mundo 09; aquí basta con eso. Un struct puede guardar referencias: una **vista** sobre datos que ya existen, sin copiarlos. Es muy eficiente, pero tiene un precio: el struct entero queda atado a la vida de lo que tiene prestado.

## Predice

<NoCompila ej="m08/p-struct-sin-lifetime" explicacion={"El campo `parte` es una referencia. Piensa: cuando alguien tenga un `Extracto`, ¿cómo sabrá hasta cuándo puede usarlo?"} />

## La idea

Si un struct guarda una referencia, su definición tiene que declarar una **lifetime genérica** y usarla en el campo:

```rust
struct Extracto<'a> {
    parte: &'a str,
}
```

Se lee: «un `Extracto<'a>` tiene prestado un texto válido durante `'a`». La consecuencia es la regla de siempre, aplicada al struct entero:

> **Un valor de tipo `Extracto<'a>` no puede usarse fuera de `'a`.**

Si el texto prestado muere, el extracto no puede usarse después:

<NoCompila ej="m08/p-struct-sobrevive" explicacion="`e` tiene prestado un trozo de `novela`, que muere al cerrar el bloque. Usar `e.parte` después sería leer memoria liberada. El arreglo hace que `novela` viva tanto como `e`." />

## Pruébalo

A veces un struct presta de **dos** sitios con vidas distintas. Con una sola lifetime, quedarían atados. Con dos, cada referencia mantiene la suya:

<Ejecutar ej="m08/p-struct-dos-lifetimes" />

`clave` devuelve `&'a str`, atada solo a `k`. Por eso `c` puede usarse fuera del bloque, aunque `v` (y el propio `p`) ya hayan muerto. Con `struct Par<'a> { clave: &'a str, valor: &'a str }`, `'a` sería la vida de la más corta y `c` no podría salir del bloque.

## Bajo el capó

<BajoElCapo>

**El tamaño no cambia.** Un `Extracto<'a>` ocupa exactamente lo mismo que un `&str`: dirección y longitud. La lifetime es solo información para el compilador.

**Ojo con `Drop`.** Si un struct con referencias implementa `Drop`, su destructor se ejecuta en la `}`, y el compilador cuenta eso como un **uso**: las referencias tienen que seguir válidas hasta ahí. Sin `Drop`, el struct deja de contar en su último uso (NLL). Esta comprobación tiene nombre: *drop check*. La verás a fondo en el mundo 20.

**Los tipos con lifetime son tipos distintos.** `Extracto<'a>` y `Extracto<'b>` son, para el compilador, dos tipos diferentes, relacionados por la **varianza** (lección 11): un `Extracto` con una lifetime larga puede usarse donde se pide uno con una corta.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Poner referencias en todos los structs">

Una vez que aprendes los structs con lifetime, parece elegante usar `&str` en todos los campos «para no copiar». Pronto te encontrarás con que no puedes devolver esos structs, ni guardarlos en un `Vec` que viva más que el texto original, ni moverlos a otro hilo.

❌ `struct Usuario<'a> { nombre: &'a str }` para un usuario que vive todo el programa.

✅ `struct Usuario { nombre: String }`. El struct es **dueño** de sus datos y vive lo que quiera. Usa structs con referencias para **vistas cortas** sobre datos que ya tienes: un analizador que recorre un texto, un iterador, un resultado de búsqueda.

</Trampa>
