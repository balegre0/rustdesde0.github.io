Recorrer una colección parece trivial, pero en Rust hay tres formas y cada una dice algo distinto sobre la **propiedad**: mirar, modificar o quedarse con los elementos.

## La idea

| Escribes | Equivale a | Cada `x` es | El vector, después |
|---|---|---|---|
| `for x in &v` | `v.iter()` | `&T` | intacto |
| `for x in &mut v` | `v.iter_mut()` | `&mut T` | modificado |
| `for x in v` | `v.into_iter()` | `T` | **consumido** |

Con los mapas igual, pero cada elemento es un **par**: `&mapa` da `(&K, &V)` y `&mut mapa` da `(&K, &mut V)`. Las claves nunca se pueden modificar en un recorrido: la posición de cada entrada depende de su clave.

Para tener también el índice: `.iter().enumerate()` da `(índice, &T)`.

## Bajo el capó

<BajoElCapo>

**`for` es azúcar.** `for x in coleccion { … }` se convierte en:

```rust
let mut it = IntoIterator::into_iter(coleccion);
while let Some(x) = it.next() { … }
```

`&Vec<T>`, `&mut Vec<T>` y `Vec<T>` implementan `IntoIterator` cada uno a su manera: por eso lo que pongas detrás de `in` decide si se presta o se consume. Lo verás a fondo en el mundo 14.

**El recorrido mantiene el préstamo.** Mientras dura `for x in &v`, el iterador guarda un préstamo de `v`. Por eso no puedes hacer `v.push(…)` dentro del bucle:

<NoCompila ej="m11/modificar-mientras" explicacion="El préstamo compartido del recorrido vive todo el bucle, y `push` necesita uno exclusivo. Si `push` reubicara el vector, el recorrido seguiría leyendo memoria liberada." />
