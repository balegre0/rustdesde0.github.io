Hasta ahora has visto el compilador como una cadena de etapas. Es una buena imagen para aprender, pero el `rustc` real está organizado de otra forma: como un conjunto de **preguntas** que se hacen unas a otras y recuerdan sus respuestas. Esa organización es la que permite recompilar rápido cuando cambias una línea.

## La idea

En `rustc`, casi todo es una **query**: `type_of(id)` («¿qué tipo tiene esto?»), `typeck(función)`, `mir_built(función)`, `mir_borrowck(función)`, `optimized_mir(función)`, `codegen_unit(nombre)`… Cuando una etapa necesita algo, **lo pide**, y la query se calcula en ese momento si nadie la había pedido antes (*bajo demanda*). El resultado queda guardado (*memoizado*), así que cada pregunta se responde una sola vez.

Mientras una query se ejecuta, rustc anota **qué otras queries consulta**. Así construye un **grafo de dependencias**. Al recompilar, usa el algoritmo **rojo-verde**: para cada resultado guardado, comprueba si alguna de sus entradas cambió. Si ninguna cambió, la query es **verde** y su resultado se carga del disco (carpeta `target/debug/incremental`). Si alguna cambió, es **roja** y se recalcula. Cambiar el cuerpo de una función no obliga a recalcular el tipo de las demás, porque `type_of` de otra función no dependía de ese cuerpo.

¿Y por qué tarda tanto compilar Rust? Las causas principales: la **monomorfización** genera mucho código para LLVM; **LLVM** optimizando es la fase más cara en release; el **enlazado** de binarios grandes; las **macros procedurales** y los `build.rs`, que son programas que se compilan y se ejecutan; y crates enormes que no se pueden repartir entre núcleos.

## Bajo el capó

<BajoElCapo>

**Todo gira alrededor de `TyCtxt`.** El contexto central del compilador se llama `TyCtxt<'tcx>` y las queries son métodos suyos: `tcx.type_of(def_id)`, `tcx.optimized_mir(def_id)`. Los tipos se guardan **internados** en una arena: cada tipo distinto existe una sola vez en memoria, así que comparar dos tipos es comparar dos punteros. La lifetime `'tcx` es la de esa arena.

**Identificadores estables.** Para reutilizar resultados entre una compilación y la siguiente, rustc no puede usar números que cambian (como el `DefId(0:3)` que viste en el THIR). Usa `DefPathHash`, un hash estable de la **ruta** de cada definición, y huellas de 128 bits (*fingerprints*) de los resultados.

**Medir, siempre antes de tocar:**

- `cargo build --timings`: informe HTML por crate, con el paralelismo. Es lo primero.
- `cargo check` en lugar de `build` mientras editas: solo produce `.rmeta` (metadatos), sin LLVM ni enlazado. El `--emit=metadata` que usa este curso para verificar código es lo mismo.
- Con nightly, `-Zself-profile` registra cuánto tarda cada query; las herramientas de `measureme` lo resumen.
- `cargo llvm-lines` (lección 8) para encontrar genéricos que inflan el IR.

**Palancas típicas en `Cargo.toml`:**

```toml
[profile.dev]
debug = "line-tables-only"   # menos información de depuración

[profile.dev.package."*"]
opt-level = 2                # optimiza las dependencias una vez; tu código sigue rápido de compilar
```

Más: dividir un crate grande en varios de un *workspace* (se compilan en paralelo y se cachean por separado), usar un enlazador más rápido, y el backend Cranelift para debug (lección 9).

**Lo que viene.** El proyecto tiene en 2026 una hoja de ruta de «compilaciones rápidas»: un **frontend paralelo** (que las queries de distintas funciones se calculen a la vez en varios hilos; en nightly se prueba con `-Zthreads=8`), Cranelift listo para producción y mejoras de enlazado. El rendimiento del compilador se vigila en https://perf.rust-lang.org/, donde se mide cada cambio que entra.

**rust-analyzer** (el que usa tu editor) no usa las queries de rustc: tiene su propio motor incremental, **salsa**, con la misma idea de fondo, y reutiliza algunas piezas del compilador como el lexer.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Hacer `cargo clean` cada vez que algo va lento o raro">

❌ Borrar `target/` «por si acaso» antes de cada compilación.

✅ Borrar `target/` tira a la basura toda la caché incremental y todas las dependencias compiladas: la siguiente compilación es la más lenta posible. La incrementalidad está diseñada para ser correcta; si sospechas de un fallo, mide con `--timings` primero. (Si encuentras un caso real en que la caché da un resultado incorrecto, es un error del compilador digno de informe.)
