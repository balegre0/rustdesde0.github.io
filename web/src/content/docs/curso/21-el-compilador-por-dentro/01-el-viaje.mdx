`rustc` no lee tu programa una vez y escupe un ejecutable. Lo transforma **muchas veces**, y cada forma intermedia existe para responder una pregunta concreta. En esta lección recorres el viaje entero con un programa de seis líneas.

## La idea

El compilador es una **cadena de traducciones**. Cada etapa recibe una representación del programa y produce otra más fácil de analizar:

1. **Lexer**: texto → *tokens* (palabras sueltas: `let`, `v`, `=`, `[`, `10`…). Pregunta: ¿son válidos estos caracteres?
2. **Parser**: tokens → **AST** (*abstract syntax tree*, árbol de sintaxis abstracta). Pregunta: ¿tiene forma de Rust?
3. **Expansión de macros y resolución de nombres**: las macros (`println!`, `vec!`, `#[derive]`) se sustituyen por código, y cada nombre se une a lo que significa. Pregunta: ¿existe cada cosa que nombras?
4. **HIR** (*high-level IR*, representación intermedia de alto nivel): el AST sin azúcar. `for`, `?` y `while let` ya no existen.
5. **Comprobación de tipos** (*typeck*) y **THIR** (*typed HIR*): cada expresión recibe su tipo, cada método se resuelve, cada conversión implícita se escribe. Pregunta: ¿cuadran los tipos? ¿se cumplen los traits?
6. **MIR** (*mid-level IR*): un **grafo** de bloques básicos. Aquí trabajan el borrow checker, la evaluación de `const` y muchas optimizaciones. Pregunta: ¿es seguro cada camino de ejecución?
7. **Monomorfización y codegen**: se crean las copias concretas de tus genéricos y se traducen a **LLVM IR**, que LLVM convierte en código máquina.
8. **Enlazado** (*linking*): los trozos de código máquina (tuyos y de `std`) se unen en un ejecutable.

Fíjate en el patrón: **cada error que conoces pertenece a una etapa**. E0765 (cadena sin cerrar) es del lexer; E0425 (nombre que no existe) es de la resolución de nombres; E0308 (tipos que no cuadran) es de typeck; E0499 y E0502 (préstamos) son del borrow checker sobre MIR. Saber en qué etapa está un error te dice qué clase de cosa está mal.

Para verlo en tu ordenador necesitas la toolchain nightly (solo para mirar):

```bash
rustup toolchain install nightly
rustc +nightly --edition 2024 -Zunpretty=expanded viaje.rs   # tras expandir macros
rustc +nightly --edition 2024 -Zunpretty=hir viaje.rs        # el HIR
rustc --edition 2024 --emit=mir viaje.rs                     # el MIR (¡funciona con stable!)
```

## Bajo el capó

<BajoElCapo>

Salida real de `rustc +nightly --edition 2024 -Zunpretty=expanded` (nightly 1.101.0, noviembre de 2026). La macro `println!` ya es una llamada a `::std::io::_print` con `format_args!`:

```text
fn main() {
    let v = [10, 20, 30];
    for x in v { { ::std::io::_print(format_args!("{0}\n", x)); }; }
}
```

Y la salida real de `-Zunpretty=hir`, donde el `for` **ya no existe**:

```text
fn main() {
    let v = [10, 20, 30];
    {
        let _t =
            match into_iter(v) {
                mut iter =>
                    loop {
                        match next(&mut iter) {
                            None {} => break,
                            Some {  0: x } => {
                                {
                                    ::std::io::_print({
                                            super let args = (&x,);
                                            super let args = [format_argument::new_display(args.0)];
                                            unsafe { format_arguments::new(b"\xc0\x01\n\x00", &args) }
                                        });
                                };
                            }
                        }
                    },
            };
        _t
    }
}
```

Tres cosas que leer aquí:

- `into_iter` y `next` son `IntoIterator::into_iter` e `Iterator::next`. Por eso **cualquier** tipo que implemente `IntoIterator` sirve en un `for`.
- `super let` es una construcción interna que usan las macros de `std` para alargar la vida de un temporal. No la puedes escribir en código estable.
- `b"\xc0\x01\n\x00"` es la plantilla de formato codificada en bytes. Este detalle **cambia entre versiones**: no lo memorices, aprende a generarlo.

El código del compilador está organizado por etapas en crates con nombre propio: `rustc_lexer` y `rustc_parse` (lexer y parser), `rustc_expand` y `rustc_resolve` (macros y nombres), `rustc_ast_lowering` (AST → HIR), `rustc_hir_typeck` (tipos dentro de las funciones), `rustc_mir_build` (THIR → MIR), `rustc_borrowck`, `rustc_mir_transform` (optimizaciones de MIR), `rustc_monomorphize` y `rustc_codegen_llvm`. La guía oficial para contribuir, la *rustc-dev-guide*, sigue este mismo orden.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Creer que el fallo está exactamente en la línea del error">

❌ «El compilador dice línea 4, así que el fallo está en la línea 4.»

✅ El error aparece donde **la etapa que lo detecta** se dio cuenta. El lexer se pierde después de la comilla que falta; el borrow checker señala el uso que choca, y en otra etiqueta el préstamo que lo causa. Lee todas las marcas del mensaje (`-`, `^`, `note:`, `help:`), no solo la primera línea.

</Trampa>
