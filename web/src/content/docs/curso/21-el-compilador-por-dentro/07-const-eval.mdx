El compilador de Rust lleva dentro un **intérprete**: puede ejecutar parte de tu código mientras compila y guardar el resultado como si fuera un número que tú hubieras escrito. Así se calculan las `const`, los `static` y el tamaño de los arrays.

## La idea

Una `const fn` es una función que **también** se puede ejecutar al compilar. Cuando la usas para dar valor a un `const`, un `static`, la longitud de un array o un bloque `const { … }`, el compilador:

1. construye su MIR, como para cualquier función;
2. lo ejecuta en su **intérprete de MIR** (el crate `rustc_const_eval`), con una memoria simulada;
3. si todo va bien, guarda el resultado y lo usa como si fuera un literal.

El intérprete es **estricto**: cualquier pánico, división por cero, acceso fuera de límites o `assert` fallido es un error de compilación. (Con el overflow hay un matiz importante que verás abajo.) Dentro de una `const fn` no puedes hacer cosas que dependan del mundo exterior (leer archivos, la hora, reservar memoria del heap para que sobreviva…), porque al compilar no hay mundo exterior.

Ventaja práctica: lo que se calcula en compilación **no cuesta nada al ejecutar**. Una tabla precalculada, una comprobación de tamaños o un valor derivado de otras constantes se convierten en datos fijos del binario.

## Bajo el capó

<BajoElCapo>

**El error real.** Con `const F21: u64 = factorial(21);`, rustc 1.99.1 dice:

```text
error[E0080]: attempt to compute `2432902008176640000_u64 * 21_u64`, which would overflow
  --> const-desborda.rs:12:18
   |
12 | const F21: u64 = factorial(21);
   |                  ^^^^^^^^^^^^^ evaluation of `F21` failed inside this call
   |
note: inside `factorial`
  --> const-desborda.rs:5:9
   |
 5 |         r *= i;
   |         ^^^^^^ the failure occurred here
```

Fíjate en el detalle: el mensaje muestra los **valores concretos** de la multiplicación que desbordó (20! × 21). Solo un intérprete que está ejecutando de verdad el código puede saberlo. Y señala una **pila de llamadas** (`inside factorial`), como un pánico, pero en tiempo de compilación.

**La sorpresa de release.** El intérprete ejecuta **el MIR tal como se construyó**. Compilando con `-O -C overflow-checks=off` (lo que hace `cargo build --release`), el MIR de `factorial` ya no tiene `MulWithOverflow` + `assert`, sino una multiplicación que da la vuelta. Lo comprobamos: el mismo archivo **compila** en release y el programa imprime `14197454024290336768`, que es 21! módulo 2⁶⁴. En cambio, una operación escrita directamente en la constante, como `const X: u8 = 255 + 1;`, sigue dando E0080 también con `overflow-checks=off` (`attempt to compute u8::MAX + 1_u8, which would overflow`). Moraleja: si una `const fn` puede desbordar, usa `checked_mul` o `strict_mul`, o pon tus constantes a prueba con un `assert!` dentro de la constante.

**Comprobaciones de tamaño gratis.** El truco más útil para mirar por dentro del compilador sin ejecutar nada:

```rust
const _: () = assert!(std::mem::size_of::<Option<&u8>>() == 8);
```

Si la condición es falsa, la compilación falla con E0080. En la lección 10 (layout) verificamos así una tabla de tamaños de x86-64 entera, compilando solo con `--emit=metadata`.

**El mismo motor que Miri.** El intérprete de `rustc_const_eval` está escrito de forma genérica sobre una «máquina» con ganchos. La evaluación de constantes usa una máquina estricta que solo permite lo que tiene sentido al compilar. **Miri** (la herramienta del mundo 20) usa el mismo intérprete con otra máquina que añade la detección de comportamiento indefinido: punteros colgantes, lecturas sin inicializar, violaciones del modelo de aliasing. Por eso Miri puede ejecutar tus tests «a cámara lenta» y avisarte de UB.

</BajoElCapo>

<Trampa titulo="Confundir `const` con `let` inmutable">

❌ «`const X: u32 = 5;` y `let x = 5;` son lo mismo.»

✅ Un `let` se evalúa **al ejecutar**, cada vez que pasa por ahí, y puede depender de la entrada. Un `const` se evalúa **al compilar**, una vez, y su valor se copia en cada sitio donde se usa. Por eso un `const` no puede depender de nada que solo se sepa en tiempo de ejecución.

</Trampa>
