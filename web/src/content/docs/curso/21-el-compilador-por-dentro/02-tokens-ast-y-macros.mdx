Las dos primeras etapas del compilador convierten una tira de caracteres en un **árbol**. En esta lección escribes un lexer y un parser de juguete que hacen lo mismo que los de `rustc` en pequeño, y luego ves cómo el compilador expande macros y resuelve nombres sobre ese árbol.

## La idea

**El lexer** (*analizador léxico*) recorre los caracteres y los agrupa en **tokens**: un identificador (`total`), un literal (`12`, `"hola"`), un signo (`+`, `=>`, `::`), un delimitador (`(`, `{`). No sabe nada de significado: `totl` es un identificador perfectamente válido para él. En rustc vive en el crate `rustc_lexer`, que es pequeño y no depende del resto del compilador.

**El parser** (*analizador sintáctico*) lee los tokens y construye el **AST**. Su trabajo principal es decidir **quién contiene a quién**. En `1 + 2 * 3` el árbol es un `+` cuyo hijo derecho es un `*`, porque la multiplicación tiene más **precedencia**. El parser de rustc está escrito a mano (no lo genera ninguna herramienta) en `rustc_parse`, y usa descenso recursivo: una función por cada tipo de construcción, que se llaman entre sí.

Después vienen dos tareas que se hacen **juntas y en bucle**: la **expansión de macros** (cada `println!`, `vec!` o `#[derive(Debug)]` se sustituye por el código que genera) y la **resolución de nombres** (cada `x`, `Vec`, `std::io` se une a su definición). Van juntas porque se necesitan mutuamente: para expandir `mi_macro!` hay que saber qué es `mi_macro`, y la expansión puede crear funciones, structs o incluso otras macros. Se repite hasta que no queda nada sin expandir.

La clave está en `expr(minimo)`: solo se queda con un operador si «pega» más fuerte que `minimo`. Al leer el `*` de `1 + 2 * 3` estamos dentro de la llamada del `+` (mínimo 1) y `*` tiene 2, así que el `*` se mete **dentro** del hijo derecho del `+`.

## Bajo el capó

<BajoElCapo>

**El AST real.** Con nightly puedes volcar el árbol de rustc. Para `fn f() -> i32 { 1 + 2 * 3 }`, un fragmento real de `rustc +nightly --crate-type lib -Zunpretty=ast-tree` (147 líneas en total):

```text
kind: Binary(
    Spanned {
        node: Add,
        span: expr.rs:1:19: 1:20 (#0),
    },
    Expr {
        kind: Lit(
            Lit {
                kind: Integer,
                symbol: "1",
                suffix: None,
            },
        ),
        span: expr.rs:1:17: 1:18 (#0),
    },
    Expr {
        kind: Binary(
            Spanned {
                node: Mul,
                span: expr.rs:1:23: 1:24 (#0),
            },
            ...
```

Cada nodo guarda su **span**: archivo, línea y columna de inicio y fin. Así es como un error puede subrayar exactamente `^^^^` el trozo culpable aunque ocurra diez etapas más tarde. El `(#0)` es el **contexto de sintaxis** del span, la pieza que hace funcionar la higiene: los tokens creados por una macro llevan otro número.

**La expansión real.** Con `-Zunpretty=expanded` (lo mismo que hace la herramienta `cargo expand`) se ve el resultado. Para `cuadrado!(2 + 1)` y un `#[derive(Debug, Clone)]` sobre `struct P { x: i32 }`, salida real:

```text
#[automatically_derived]
impl ::core::clone::Clone for P {
    #[inline]
    fn clone(&self) -> Self { P { x: ::core::clone::Clone::clone(&self.x) } }
}
fn main() {
    ...
    let c = (2 + 1) * (2 + 1);
```

El paréntesis de `(2 + 1)` lo pone el impresor para mostrar que el nodo ya estaba agrupado. Y el código derivado usa rutas absolutas (`::core::clone::Clone`) para no depender de lo que tengas importado: otra forma de higiene.

**Macros procedurales.** Un `#[derive]` propio, un atributo o una macro tipo función de un crate `proc-macro` se compila como una biblioteca aparte que rustc **carga y ejecuta** durante la expansión, pasándole los tokens por un puente (`proc_macro::bridge`). Por eso las macros procedurales cuestan tiempo de compilación: son programas que corren dentro del compilador.

</BajoElCapo>

<Trampa titulo="Pensar que una macro es «buscar y reemplazar» texto">

❌ «`cuadrado!(2 + 1)` se convierte en `2 + 1 * 2 + 1`.»

✅ Las macros reciben y producen **árboles de tokens**. Un fragmento `$e:expr` es un nodo completo y se inserta como tal. Por eso las macros de Rust no necesitan llenar todo de paréntesis por precaución.
