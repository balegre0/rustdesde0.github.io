Después de expandir macros, el compilador hace *lowering*: reescribe el AST en una forma más pequeña, el **HIR**, donde muchas construcciones se expresan con otras más básicas. Luego comprueba los tipos y produce el **THIR**, donde nada queda implícito. En esta lección escribes tú mismo esas traducciones.

## La idea

**El HIR** es el árbol después de quitar el azúcar sintáctico (*desugaring*). Algunas traducciones:

- `for pat in expr { cuerpo }` → `match IntoIterator::into_iter(expr) { mut iter => loop { match Iterator::next(&mut iter) { None => break, Some(pat) => cuerpo } } }`
- `expr?` → `match Try::branch(expr) { Continue(v) => v, Break(r) => return FromResidual::from_residual(r) }`
- `while let pat = expr { … }` → `loop { match expr { pat => …, _ => break } }`
- `async fn f() -> T` → una función que devuelve `impl Future<Output = T>` (lo verás en la lección 12).

Con menos construcciones, las etapas siguientes tienen menos casos que tratar. Por eso el borrow checker no necesita saber nada de `for`: solo ve `loop` y `match`.

**La comprobación de tipos** recorre el HIR de cada función. Para cada expresión cuyo tipo no conoce todavía crea una **variable de inferencia** y la va igualando con lo que exige cada uso (*unificación*): si pasas `v` a una función que espera `&[u32]`, eso fija el tipo. También **resuelve métodos**: `x.len()` tiene que convertirse en una función concreta, quizá tras añadir `&` o `*` automáticamente (*autoref* y *autoderef*).

**El THIR** es el resultado: un árbol solo de cuerpos, donde cada nodo lleva su tipo, cada `.metodo()` es una llamada normal a una ruta concreta y cada conversión implícita (como `&String` → `&str`) está escrita. Sobre el THIR se comprueban la **exhaustividad de los `match`** y las **operaciones `unsafe`**, y de él se construye el MIR.

## Bajo el capó

<BajoElCapo>

**El HIR real de `?`.** Para `fn doble(s: &str) -> Result<i32, ParseIntError> { let n: i32 = s.parse()?; Ok(n * 2) }`, salida real de `rustc +nightly -Zunpretty=hir` (nightly 1.101.0):

```text
fn doble(s: &'_ str)
    ->
        Result<i32,
        std::num::ParseIntError> {
    let n: i32 =
        match branch(s.parse()) {
            Break {  0: residual } => return from_residual(residual),
            Continue {  0: val } => val,
        };
    Ok(n * 2)
}
```

Fíjate en `&'_ str`: el lowering ya hizo explícita la **lifetime elidida** que no escribiste.

**El THIR real.** Para `fn suma(a: u8, b: u8) -> u32 { (a + b).into() }`, un fragmento real de `rustc +nightly -Zunpretty=thir-tree` (171 líneas en total; quitamos los `span`):

```text
Call {
    ty: FnDef(DefId(2:4071 ~ core[4712]::convert::Into::into), Binder { value: [u8, u32], bound_vars: [] })
    from_hir_call: true
    fun:
        Expr {
            ty: FnDef(DefId(2:4071 ~ core[4712]::convert::Into::into), ...)
            kind: ZstLiteral(user_ty: None)
        }
    args: [
        Expr {
            ty: u8
            kind:
                Binary {
                    op: Add
                    lhs: ... VarRef { id: LocalVarId(...) } ...
```

Lo que tú escribiste como `.into()` aquí ya es una **llamada a una función concreta**: `core::convert::Into::into` con los argumentos de tipo `[u8, u32]` (es decir, `<u8 as Into<u32>>::into`). El `DefId(2:4071)` identifica la definición: crate número 2 (`core`), elemento 4071. Y cada expresión lleva su `ty:`. Nada se deja a la imaginación de las etapas siguientes.

## Trampa típica

<NoCompila ej="m21/tipos-no-cuadran" explicacion="E0308 es de la comprobación de tipos: unificar el tipo del argumento (`u8`) con el de la firma (`u32`) falla. Rust no convierte números por su cuenta: el `help:` te propone `.into()`, una conversión explícita sin pérdida." />

<Trampa titulo="Creer que la inferencia «adivina» tipos mirando todo el programa">

❌ «Rust deduce los tipos de mis funciones a partir de cómo las uso en otros sitios.»

✅ La inferencia trabaja **dentro de cada cuerpo de función**. Las firmas (`fn area(lado: u32) -> u32`) se escriben siempre completas, y son el contrato que cada cuerpo comprueba por separado. Gracias a eso, cambiar el interior de una función no puede romper los tipos de otra.

</Trampa>
