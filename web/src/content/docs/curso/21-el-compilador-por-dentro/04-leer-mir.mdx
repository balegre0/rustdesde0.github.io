El MIR es la representación donde Rust se vuelve **Rust de verdad**: aquí se comprueban los préstamos, se insertan los `drop`, se evalúan las constantes y se hacen las primeras optimizaciones. Y lo mejor: puedes generarlo con la toolchain estable. En esta lección aprendes a leerlo línea a línea.

## La idea

El MIR de una función es un **grafo de flujo de control** (*control-flow graph*, CFG). Tiene tres ingredientes:

- **Locales**: casillas numeradas. `_0` es el valor que se devuelve; `_1`, `_2`… son los argumentos, y luego las variables y los temporales que el compilador necesita. Las líneas `debug x => _1;` dicen qué variable tuya corresponde a cada local.
- **Bloques básicos** (`bb0`, `bb1`…): listas de **sentencias** simples (asignar, leer un campo, calcular) que se ejecutan siempre en orden.
- **Terminadores**: la última línea de cada bloque, y la única que puede cambiar de camino: `goto -> bbN` (salto), `switchInt` (el `match`), `call` (llamada que vuelve a un bloque), `assert` (comprobación que puede entrar en pánico), `drop` (destruir un valor), `return` y `unreachable`.

Además, los **operandos dicen cómo se usan los valores**: `copy _3` copia un valor `Copy`; `move _1` lo mueve (después `_1` ya no vale); `&_2` crea un préstamo compartido. Con esto el borrow checker tiene todo lo que necesita: quién se movió, quién está prestado y por qué caminos.

## Bajo el capó

<BajoElCapo>

Salida real de rustc 1.99.1 para `doble`. La propia cabecera avisa: es un formato para humanos que puede cambiar sin aviso.

```text
fn doble(_1: Option<u32>) -> u32 {
    debug x => _1;
    let mut _0: u32;
    let mut _2: isize;
    let _3: u32;
    let mut _4: (u32, bool);
    scope 1 {
        debug n => _3;
    }

    bb0: {
        _2 = discriminant(_1);
        switchInt(move _2) -> [0: bb2, 1: bb3, otherwise: bb1];
    }

    bb1: {
        unreachable;
    }

    bb2: {
        _0 = const 0_u32;
        goto -> bb5;
    }

    bb3: {
        _3 = copy ((_1 as Some).0: u32);
        _4 = MulWithOverflow(copy _3, const 2_u32);
        assert(!move (_4.1: bool), "attempt to compute `{} * {}`, which would overflow", copy _3, const 2_u32) -> [success: bb4, unwind continue];
    }

    bb4: {
        _0 = move (_4.0: u32);
        goto -> bb5;
    }

    bb5: {
        return;
    }
}
```

Léelo así: `discriminant(_1)` lee la **etiqueta** del enum; `switchInt` es el `match`. `(_1 as Some).0` es una **proyección**: «el campo 0 de `_1` vista como variante `Some`». La multiplicación con comprobación devuelve una tupla `(resultado, hubo_overflow)` y el `assert` tiene dos salidas: `success` y `unwind`, el camino que se sigue si hay pánico.

Ahora una función que **posee** un `String`:

```rust
pub fn saluda(nombre: String) -> usize {
    let s = nombre;
    s.len()
}
```

Su MIR real:

```text
fn saluda(_1: String) -> usize {
    debug nombre => _1;
    let mut _0: usize;
    let _2: std::string::String;
    let mut _3: &std::string::String;
    scope 1 {
        debug s => _2;
    }

    bb0: {
        _2 = move _1;
        _3 = &_2;
        _0 = String::len(move _3) -> [return: bb1, unwind: bb3];
    }

    bb1: {
        drop(_2) -> [return: bb2, unwind continue];
    }

    bb2: {
        return;
    }

    bb3 (cleanup): {
        drop(_2) -> [return: bb4, unwind terminate(cleanup)];
    }

    bb4 (cleanup): {
        resume;
    }
}
```

Aquí ves la **propiedad** hecha código: `_2 = move _1` (mover), `&_2` (préstamo compartido para llamar a `len`, con el autoref ya explícito), y `drop(_2)` al final, que libera la memoria del `String`. Y fíjate: **no hay `drop(_1)`**, porque `_1` se movió. Así evita Rust la **doble liberación**. Si `len` entrara en pánico, se iría por `unwind: bb3`, un bloque `cleanup` que también hace `drop(_2)` (sin fugas de memoria) y termina en `resume` para seguir desenrollando.

Con nightly puedes ver el MIR **en cada pasada** del compilador con `-Zdump-mir=doble` (escribe un archivo por pasada en la carpeta `mir_dump/`) o dibujarlo con `-Zdump-mir-graphviz`. El `--emit=mir` muestra la última versión, el MIR optimizado.

</BajoElCapo>

## Trampa típica

<NoCompila ej="m21/sin-inicializar" explicacion="E0381 lo detecta un análisis de flujo sobre MIR: existe un camino (si `llueve` fuera `false`) que llega al uso de `x` sin pasar por ninguna asignación. El compilador no evalúa la condición; mira los caminos del grafo. Leer memoria sin inicializar sería comportamiento indefinido." />

<Trampa titulo="Pensar que el compilador «ve» que una condición siempre es verdadera">

❌ «`llueve` es `true`, así que `x` siempre tiene valor; el compilador debería saberlo.»

✅ Los análisis del MIR razonan sobre **todos los caminos del grafo**, no sobre los valores. Es una aproximación segura: puede rechazar programas correctos, pero nunca acepta uno que lea memoria sin inicializar. El arreglo es que **cada** camino dé valor, por ejemplo con `if … { 1 } else { 0 }`.

</Trampa>
