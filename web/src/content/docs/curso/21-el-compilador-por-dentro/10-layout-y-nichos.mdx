El compilador decide cuántos bytes ocupa cada tipo y dónde va cada campo: el **layout**. Esa decisión tiene trucos muy finos, como guardar el `None` de un `Option` dentro de un valor imposible. Hoy vas a medirlo todo.

## La idea

Cada tipo tiene un **tamaño** y un **alineamiento** (la dirección donde empieza debe ser múltiplo de él). Un `u32` mide 4 y se alinea a 4. Un struct se construye colocando sus campos y añadiendo **relleno** (*padding*) donde haga falta para que cada campo quede alineado.

Con el layout por defecto, `repr(Rust)`, el compilador puede **reordenar los campos** como quiera. Lo usa para ahorrar relleno: `struct { a: u8, b: u32, c: u16 }` en orden de declaración necesitaría 12 bytes, pero colocando primero `b`, luego `c` y luego `a`, caben en 8. Si necesitas un orden fijo (para hablar con el sistema operativo o con hardware), pides `#[repr(C)]`: orden de declaración con las reglas de relleno de la plataforma.

Los enums necesitan saber **qué variante** contienen: una **etiqueta** (*discriminante*). Pero si alguna variante tiene un campo con **valores imposibles**, rustc puede guardar ahí la etiqueta. A esos valores se les llama **nichos** (*niches*): el 0 de una referencia o de un `Box`, los valores 2–255 de un `bool`, los números por encima de 0x10FFFF de un `char`, el 0 de un `NonZeroU32`. Así, `Option<bool>` cabe en 1 byte (`None` se guarda como, por ejemplo, el valor 2).

## Bajo el capó

<BajoElCapo>

**La misma tabla en x86-64.** La verificamos con rustc 1.99.1 en x86-64 Windows **sin ejecutar nada**: una aserción por tipo evaluada al compilar (lección 7). Si cualquier número fuera falso, la compilación fallaría con E0080.

```rust
macro_rules! chk { ($t:ty, $s:expr, $a:expr) => {
    const _: () = assert!(size_of::<$t>() == $s && align_of::<$t>() == $a);
} }
chk!(Option<&u8>, 8, 8);  // y así con cada fila
```

| Tipo | wasm32 (navegador) | x86-64 |
|---|---|---|
| `bool` / `char` | 1 / 4 | 1 / 4 |
| `u128` | 16 (alineamiento 16) | 16 (alineamiento 16) |
| `usize`, `&u8`, `Option<&u8>` | 4 | 8 |
| `Option<*const u8>` | 8 | **16** |
| `Option<u32>` | 8 | 8 |
| `Option<NonZeroU32>` | 4 | 4 |
| `Option<bool>`, `Option<Option<bool>>` | 1 | 1 |
| `Option<char>` | 4 | 4 |
| `struct { a: u8, b: u32, c: u16 }` | 8 | 8 |
| ídem con `#[repr(C)]` | 12 | 12 |
| `enum { A(Box<u64>), B }` | 4 | 8 |
| `enum { A(Box<u64>), B, C }` | 8 | **16** |
| `Vec<u8>`, `Option<Vec<u8>>` | 12 | 24 |
| `&str`, `&dyn Debug` | 8 | 16 |

Cosas que leer en la tabla:

- **Un puntero aporta un solo nicho.** `Box<u64>` está alineado a 8, así que sus 3 bits bajos siempre son 0; aun así rustc solo usa el valor 0 como nicho. Con una variante sin datos (`B`) basta; con dos (`B`, `C`) ya no, y el enum crece con una etiqueta aparte.
- `Option<Vec<u8>>` no crece: el puntero interno de `Vec` nunca es nulo y la capacidad nunca supera `isize::MAX`, así que sobran valores imposibles.
- `Option<u32>` sí crece: todos los patrones de 32 bits son un `u32` válido. Por eso existe `NonZeroU32`.

**Ver el orden real.** Con nightly, `-Zprint-type-sizes` muestra cómo quedó cada tipo. Para el struct de tres campos imprime `b` (4 bytes), `c` (2), `a` (1) y 1 byte de relleno final: el orden lo ha cambiado el compilador.

**Qué está garantizado y qué no.** La Reference solo garantiza para `repr(Rust)` lo dicho arriba (alineado, sin solapes, alineamiento mínimo). Los tamaños de esta tabla son **lo que hace rustc 1.99.1**, no promesas, salvo casos documentados como el nicho de `Option<&T>`, `Option<Box<T>>`, `Option<NonZero*>` o los tipos `repr(C)`. Si tu código `unsafe` depende de un layout, usa `repr(C)` o `repr(transparent)`.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Suponer el orden de los campos en `unsafe`">

❌ Convertir un `*const MiStruct` en `*const u8`, sumar 1 y «leer el segundo campo», porque es el segundo en el código.

✅ Con `repr(Rust)` el segundo campo declarado puede estar en cualquier sitio. Usa `std::mem::offset_of!(MiStruct, campo)` para saber dónde está, o declara `#[repr(C)]` si el orden forma parte del contrato.
