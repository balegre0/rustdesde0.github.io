En el mundo 13 usaste `dyn Trait` para guardar tipos distintos en un mismo `Vec`. ¿Cómo sabe el programa qué método llamar si el tipo no se conoce al compilar? Con una **vtable**: una tabla de punteros a función. Hoy construyes una a mano y luego la buscas en el ensamblador real.

## La idea

Cuando conviertes un `&Circulo` en `&dyn Forma`, el compilador **sabe** en ese momento que el tipo es `Circulo`. Aprovecha para fabricar el puntero gordo: la dirección del círculo y la dirección de **la vtable de `Circulo` para `Forma`**, una tabla constante que generó al compilar. Hay una vtable por cada combinación de tipo concreto y trait que se usa como `dyn`.

Una llamada `f.area()` sobre un `&dyn Forma` hace tres cosas: leer la dirección de la vtable del puntero gordo, leer de la tabla la casilla de `area`, y saltar ahí pasando el puntero a los datos como `self`. Es una **llamada indirecta**: el procesador no sabe adónde va hasta que lee la tabla, y el compilador no puede inlinear el método. Es el precio de tener **una sola copia** de tu código para todos los tipos (lo contrario que la monomorfización).

La vtable no solo guarda métodos. Las tres primeras casillas son: cómo destruir el valor (`drop_in_place`), su **tamaño** y su **alineamiento**. Con ellas, un `Box<dyn Forma>` sabe liberar su memoria sin conocer el tipo.

Un `dyn Forma` construido a mano, con la misma estructura que usa rustc. (En el navegador los punteros miden 4 bytes, así que el `&dyn Fn()` del final mide 8.)

## Bajo el capó

<BajoElCapo>

El trait y la llamada reales:

```rust
pub trait Forma { fn area(&self) -> f64; fn nombre(&self) -> &'static str; }
pub struct Circulo(pub f64);
impl Forma for Circulo { /* area = 3.0 * r * r; nombre = "círculo" */ }
#[unsafe(no_mangle)] pub fn llama_area(f: &dyn Forma) -> f64 { f.area() }
#[unsafe(no_mangle)] pub fn crea() -> &'static dyn Forma { &Circulo(1.0) }
```

Ensamblador real de rustc 1.99.1 con `-O` (x86-64 Windows, sintaxis Intel), abreviado:

```text
llama_area:
	rex64 jmp	qword ptr [rdx + 24]

crea:
	lea	rax, [rip + anon.ec52ba5edbb80fa10e5d9edf22da8244.1]
	lea	rdx, [rip + anon.ec52ba5edbb80fa10e5d9edf22da8244.2]
	ret

anon.ec52ba5edbb80fa10e5d9edf22da8244.1:
	.ascii	"\000\000\000\000\000\000\360?"

anon.ec52ba5edbb80fa10e5d9edf22da8244.2:
	.asciz	"\000\000\000\000\000\000\000\000\b\000\000\000\000\000\000\000\b\000\000\000\000\000\000"
	.quad	_RNvXCs9L5mWb26O0Y_2vtNtB2_7CirculoNtB2_5Forma4area
	.quad	_RNvXCs9L5mWb26O0Y_2vtNtB2_7CirculoNtB2_5Forma6nombre
```

Léelo así:

- **La vtable** (`.2`): los primeros 24 bytes son tres palabras. La primera es **0**: `Circulo` no necesita `drop`, así que no hay función de destrucción. La segunda es `\b` = 8 (tamaño) y la tercera 8 (alineamiento), en little-endian. Detrás, un `.quad` por método en orden de declaración: `area` y `nombre`.
- **`crea`** devuelve el puntero gordo en **dos registros**: `rax` = datos (el `.1`, que contiene el `f64` 1.0: los bytes `00 … F0 3F`) y `rdx` = vtable.
- **`llama_area`** es **una sola instrucción**. El puntero gordo llega en `rcx` (datos) y `rdx` (vtable); `[rdx + 24]` es la casilla del primer método (tras 3 × 8 bytes de cabecera). Es un `jmp` y no un `call` porque es una llamada de cola: `area` devolverá el resultado directamente a quien llamó a `llama_area`.

Detalle curioso: en el mismo archivo, `nombre` hace `mov edx, 8` para devolver la longitud de `"círculo"`: son 7 letras pero **8 bytes**, porque la `í` ocupa 2 en UTF-8.

El layout de la vtable **no es estable**: puede cambiar entre versiones, y con *trait upcasting* (convertir `&dyn Sub` en `&dyn Super`) las tablas de los supertraits se combinan de formas internas. Tu código nunca debe leer una vtable a mano.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Pensar que `dyn Trait` guarda una copia del valor">

❌ «Al convertir a `&dyn Forma` se crea un objeto nuevo con los métodos dentro.»

✅ No se copia nada: el valor sigue donde estaba y la vtable es **compartida** por todos los `Circulo`. Convertir a `dyn` solo construye un par de punteros. Por eso `&dyn Trait` es un préstamo como cualquier otro, con las mismas reglas de lifetimes.

</Trampa>
