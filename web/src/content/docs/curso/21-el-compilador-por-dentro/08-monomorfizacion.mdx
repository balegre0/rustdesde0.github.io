Escribes una función genérica una vez. El compilador la escribe **muchas veces**: una por cada tipo con el que la usas. Esa es la razón de que los genéricos de Rust sean tan rápidos… y de que los proyectos grandes tarden en compilar.

## La idea

Después de construir el MIR de todas las funciones, el **recolector de monomorfización** (`rustc_monomorphize::collector`) parte de `main` (o de las funciones exportadas de una biblioteca) y recorre todo lo que se puede llegar a llamar. Cada vez que encuentra una llamada a una función genérica con tipos concretos, por ejemplo `mayor::<u8>`, añade esa **instancia** a la lista. Cada instancia se traduce por separado a código máquina, con `T` sustituido por el tipo real.

Ventajas: dentro de `mayor::<u8>` el compilador sabe que compara bytes y emite una comparación de bytes; dentro de `mayor::<f64>`, una instrucción de coma flotante. Las llamadas son **directas** y el optimizador puede **inlinearlas** (copiar el cuerpo en el sitio de la llamada) y simplificar. Por eso un iterador con tres adaptadores puede quedar igual que un bucle escrito a mano.

Costes: **más código**. Cada copia ocupa espacio en el binario y, sobre todo, cada copia es trabajo para LLVM, que es la fase más cara de la compilación. Un genérico muy usado con muchos tipos multiplica el tiempo de compilación. La alternativa es `dyn Trait`: **una** copia, y las llamadas pasan por una tabla de punteros (la vtable, lección 11), más difíciles de optimizar.

## Bajo el capó

<BajoElCapo>

Con este código:

```rust
pub fn mayor<T: PartialOrd>(a: T, b: T) -> T { if a > b { a } else { b } }
#[unsafe(no_mangle)] pub fn usa_u8(a: u8, b: u8) -> u8 { mayor(a, b) }
#[unsafe(no_mangle)] pub fn usa_f64(a: f64, b: f64) -> f64 { mayor(a, b) }
```

`rustc --edition 2024 --crate-type lib --emit=asm -C opt-level=1 -C llvm-args=-x86-asm-syntax=intel` (rustc 1.99.1, x86-64 Windows) produce, entre otras líneas:

```text
_RINvCsQRxP6z4OUx_4mono5mayordEB2_:
	maxsd	xmm0, xmm1
	ret

_RINvCsQRxP6z4OUx_4mono5mayorhEB2_:
	movzx	ecx, cl
	movzx	eax, dl
	cmp	cl, al
	cmova	eax, ecx
	ret
```

Dos copias de `mayor`, con código **totalmente distinto**: para `f64`, la instrucción de máximo de coma flotante `maxsd`; para `u8`, comparar bytes (`cmp`) y mover condicionalmente (`cmova`). Los nombres son símbolos con el formato de *mangling* v0 de Rust: `5mayor` es el nombre (5 letras) y la letra que sigue codifica el tipo del argumento genérico: `d` es `f64` y `h` es `u8`. Herramientas como `rustfilt` los traducen a `mono::mayor::<f64>`.

Además, en `usa_u8` y `usa_f64` el optimizador **inlineó** la copia correspondiente: su cuerpo es idéntico al de `mayor`, sin ninguna llamada.

**Medir el coste.** La herramienta `cargo llvm-lines` cuenta cuántas líneas de LLVM IR genera cada función genérica y cuántas copias tiene; es la forma de encontrar qué genérico está inflando tu compilación.

**El truco de `std`.** Muchas funciones de la biblioteca estándar aceptan `P: AsRef<Path>` pero hacen esto:

```rust
pub fn abrir<P: AsRef<std::path::Path>>(p: P) -> std::io::Result<std::fs::File> {
    fn interna(p: &std::path::Path) -> std::io::Result<std::fs::File> {
        std::fs::File::open(p)
    }
    interna(p.as_ref())
}
```

La parte genérica (y por tanto copiada) es una sola línea; el trabajo real está en `interna`, que existe **una sola vez**. Comodidad para quien llama, sin coste de tamaño.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Pensar que `dyn` siempre es lento y los genéricos siempre son mejores">

❌ «Uso genéricos en todas partes porque son más rápidos.»

✅ Los genéricos son más rápidos **en la llamada**, pero cada tipo añade una copia. En código que no es crítico (manejo de errores, configuración, ramas poco frecuentes), `dyn Trait` compila más rápido, ocupa menos y la diferencia en ejecución no se nota. Elige midiendo, no por dogma.

</Trampa>
