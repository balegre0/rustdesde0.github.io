## La idea

En `$nombre:clase`, la clase se llama **fragmento** (*fragment specifier*). Le dice al compilador qué tipo de trozo de código leer. Los principales:

| Fragmento | Captura | Ejemplo |
|---|---|---|
| `expr` | una expresión | `3 + 1`, `f(x)`, `if a { 1 } else { 2 }` |
| `ident` | un nombre | `x`, `contar`, `Punto` |
| `ty` | un tipo | `u32`, `Vec<String>`, `&'static str` |
| `literal` | un literal | `7`, `"hola"`, `'ñ'`, `true` |
| `block` | un bloque `{ … }` | `{ println!("hi"); }` |
| `pat` | un patrón | `Some(x)`, `1..=5`, `A \| B` |
| `path` | una ruta | `std::mem::swap` |
| `stmt` | una sentencia | `let x = 1` |
| `item` | un item | `fn f() {}`, `struct S;` |
| `lifetime` | un tiempo de vida | `'a` |
| `meta` | el interior de un atributo | `derive(Debug)` |
| `vis` | una visibilidad (puede estar vacía) | `pub`, `pub(crate)` |
| `tt` | un árbol de tokens: un token suelto o un grupo `( … )`, `[ … ]`, `{ … }` | `+`, `(a b c)` |

Una vez capturado, un fragmento (salvo `ident`, `lifetime` y `tt`) es **opaco**: se pega en la plantilla como una sola pieza ya analizada. Por eso `doble!(3 + 1)` respeta la precedencia.

## Pruébalo

<Ejecutar ej="m19/fragmentos" />

1. Con `ident` y `ty` la macro **declara una función** con el nombre y el tipo que tú elijas.
2. `literal` solo acepta literales (prueba a pasar `2 + 1` en `repite!` y verás el error) y `block` exige llaves.

### La edición 2024 cambió `expr`

<Ejecutar ej="m19/expr-2024" titulo="expr frente a expr_2021" />

Desde la edición 2024, `expr` también acepta `_` y los bloques `const { … }`, porque ahora son expresiones válidas. Para no romper macros antiguas existe `expr_2021`, que se comporta como antes. Si migras una macro y algo deja de encajar como esperabas, ese es el motivo.

## Bajo el capó

<BajoElCapo>
**Lo que ve el compilador.** La expansión real de `precedencia.rs` (Rust 1.99.1, `-Zunpretty=expanded`) es `let r = (3 + 1) * 2;`. El impresor añade los paréntesis para mostrarte algo que, en el árbol interno, ya era así: la expresión capturada es un nodo único.

**El *follow-set*.** Rust se compromete a que las macros que escribes hoy sigan funcionando cuando el lenguaje gane sintaxis nueva. Para ello limita qué puede ir **justo detrás** de ciertos fragmentos: si detrás de una `expr` pudiera ir cualquier cosa, una futura sintaxis de expresiones podría «comerse» esos tokens y cambiar el significado de tu macro. Detrás de `expr` y `stmt` solo puede ir `=>`, `,` o `;`. Detrás de `ty` y `path` hay más opciones; el compilador te las lista (salida real):

```text
error: `$t:ty` is followed by `+`, which is not allowed for `ty` fragments
  = note: allowed there are: `{`, `[`, `=>`, `,`, `>`, `=`, `:`, `;`, `|`, `as` or `where`
```

`ident`, `tt`, `literal`, `lifetime` y `block` pueden ir seguidos de cualquier cosa. La especificación formal está en el apéndice «Macro follow-set ambiguity» de la Reference.
</BajoElCapo>
