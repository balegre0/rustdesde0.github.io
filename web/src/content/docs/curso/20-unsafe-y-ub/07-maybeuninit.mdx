## La idea

En Rust seguro nunca puedes leer una variable sin inicializar: `let x: u32; println!("{x}");` es un error de compilación. Pero a veces necesitas **reservar** memoria y rellenarla poco a poco: un array grande que se calcula casilla a casilla, un búfer que llenará el sistema operativo, una estructura de datos con capacidad de sobra.

Para eso existe `MaybeUninit<T>`: un envoltorio que dice «aquí *quizá* hay un `T`». Crearlo sin inicializar (`MaybeUninit::uninit()`) es seguro, y escribir en él (`write`) también. Lo único `unsafe` es la afirmación final: `assume_init()`, «te garantizo que ya está inicializado». Si mientes, es UB.

`MaybeUninit` sustituye a la antigua `mem::uninitialized`, obsoleta desde 1.39 porque era UB para casi cualquier tipo.

## Pruébalo

<Ejecutar ej="m20/maybeuninit-array" />

(1) `[const { MaybeUninit::uninit() }; N]` crea N casillas sin inicializar (el bloque `const` permite repetir un valor que no es `Copy`); (2) `write` las rellena; (3) solo al final, con todas escritas, `assume_init` convierte cada casilla en `u64`. Y `MaybeUninit<u64>` mide 8 bytes: **no guarda** si está inicializado. Eso lo sabes tú.

## Bajo el capó

<BajoElCapo>

**Por qué no es «basura».** En la máquina abstracta, cada byte es o bien un valor `0..=255`, o bien *sin inicializar*. El compilador (y LLVM, donde se llama `undef`/`poison`) puede suponer cualquier valor distinto en cada lectura: `n == 0` y `n != 0` podrían ser **ambos** ciertos. Por eso la Reference lista «enteros, floats y punteros crudos deben estar inicializados» entre las condiciones de validez.

**`MaybeUninit<T>` es una `union`** con dos «caras»: nada o un `T`. Por eso tiene el mismo tamaño y alineación que `T`, y por eso leer el `T` requiere `unsafe` (como cualquier campo de union).

**Las APIs que conviene conocer:**

| Método | Seguro | Qué hace |
|---|---|---|
| `MaybeUninit::uninit()` | sí | casilla sin inicializar |
| `MaybeUninit::new(v)` | sí | casilla ya inicializada |
| `.write(v)` | sí | inicializa (no destruye lo que hubiera: no había nada) |
| `.as_ptr()` / `.as_mut_ptr()` | sí | puntero para que otro código escriba |
| `.assume_init()` | **no** | consume y devuelve el `T` |
| `.assume_init_read()` | **no** | copia los bits del `T` (cuidado con duplicar dueños) |
| `.assume_init_drop()` | **no** | destruye el `T` en el sitio |

</BajoElCapo>

## Trampa típica

<Trampa titulo="mem::zeroed() «para inicializar a cero»">

❌ `std::mem::zeroed()` rellena con ceros. Para un `u32` es correcto (0 es válido), pero para una referencia produce un valor inválido: un `&i32` nulo. `rustc` 1.99.1 lo detecta en este caso y avisa:

```text
warning: the type `&i32` does not permit zero-initialization
 --> zeroed-referencia.rs:5:28
  |
5 |     let r: &i32 = unsafe { std::mem::zeroed() }; // ¡MAL! referencia nula
  |                            ^^^^^^^^^^^^^^^^^^
  |                            |
  |                            this code causes undefined behavior when executed
  |                            help: use `MaybeUninit<T>` instead, and only call `assume_init` after initialization is done
  |
  = note: references must be non-null
```

✅ Usa `MaybeUninit` y afirma la inicialización solo cuando de verdad hayas escrito un valor válido. El aviso no aparece en todos los casos (por ejemplo, dentro de genéricos), así que no confíes en él como red.

</Trampa>
