## La idea

El compilador no puede ver la mayoría del UB: punteros que cuelgan, accesos fuera de límites o alias prohibidos solo se notan **al ejecutar**. Pero ejecutar en tu procesador no sirve para detectarlos: la memoria liberada sigue «ahí» un rato, un byte de más se lee sin error… y el programa parece funcionar.

**Miri** resuelve esto ejecutando el programa en una **máquina abstracta**: interpreta el MIR (la representación intermedia de `rustc`) y lleva la cuenta de todo lo que el hardware olvida: qué memoria está viva, qué bytes están inicializados, de qué asignación viene cada puntero, qué permisos de aliasing tiene, qué hilo accedió a qué. Cuando una operación incumple una regla, se detiene y señala la línea.

Es lenta (cientos de veces más que el programa nativo) y casi no admite llamadas a bibliotecas de otros lenguajes, pero para tests de código con `unsafe` es imprescindible: la biblioteca estándar la pasa en su integración continua.

## Bajo el capó

<BajoElCapo>

**Qué detecta Miri** (si el camino se ejecuta): accesos fuera de límites y uso tras liberar; lecturas de memoria sin inicializar; punteros desalineados; valores inválidos (`bool` = 2, `char` sustituto, referencias nulas…); violaciones de aliasing según Stacked Borrows (por defecto) o Tree Borrows (`-Zmiri-tree-borrows`); carreras de datos entre hilos; fugas de memoria al terminar; y uso incorrecto de provenance (`-Zmiri-strict-provenance`).

**Cómo se usa en un proyecto:**

```text
rustup +nightly component add miri
cargo +nightly miri test        # ejecuta los tests bajo Miri
cargo +nightly miri run         # ejecuta main bajo Miri
```

Banderas útiles (en la variable `MIRIFLAGS`): `-Zmiri-tree-borrows`, `-Zmiri-strict-provenance`, `-Zmiri-many-seeds` (prueba muchas planificaciones de hilos y direcciones, porque Miri sigue **una** traza cada vez).

**El límite:** Miri solo ve lo que ejecuta. Si un test no recorre el camino con UB, no lo encontrará. Por eso se combina con tests de propiedades y *fuzzing*.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Miri en Windows sin las Build Tools">

❌ La primera vez, `cargo miri` prepara su propia biblioteca estándar, y para eso **compila y enlaza** pequeños programas auxiliares. En Windows sin las *Build Tools* de Visual Studio falla con un error de `link.exe`, y desde Git Bash el mensaje es aún más confuso (`link: extra operand …`), porque encuentra otro programa llamado `link`.

✅ Instala las *Build Tools* con «Desarrollo para el escritorio con C++» y usa PowerShell, o usa WSL. Mientras tanto, el Playground tiene Miri en *Tools → Miri* y no necesita nada instalado.

</Trampa>
