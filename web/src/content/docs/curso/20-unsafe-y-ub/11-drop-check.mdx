## La idea

Al terminar un ámbito, Rust ejecuta el `drop` de cada valor, en un orden fijo: **locales en orden inverso** a su declaración; **campos de un struct en el orden declarado**. Normalmente no tienes que pensar en ello.

El problema aparece con tipos que **toman prestado** algo y además **implementan `Drop`**. Su `drop` es código tuyo y podría leer la referencia. Si lo prestado se destruye antes (o a la vez), ese `drop` leería memoria liberada. Por eso el compilador aplica la regla del **drop check**: si un tipo genérico implementa `Drop`, todo lo que toma prestado debe vivir **estrictamente más** que él.

Sin `Drop`, el compilador sabe que destruir el tipo no ejecuta código que mire la referencia, y es más permisivo.

## Bajo el capó

<BajoElCapo>

**La regla precisa.** Para un `impl<T> Drop for MiTipo<T>`, el compilador asume lo peor: que `drop` puede **usar** cualquier `T` (y cualquier referencia dentro). Por eso exige que todo lo que `MiTipo` toma prestado esté vivo cuando se ejecute su `drop`.

**¿Y `Vec`?** `Vec<&str>` implementa `Drop`, pero puedes tener un `Vec` de referencias a cosas que mueren a la vez que el vector. ¿Cómo? La biblioteca estándar usa un atributo **inestable**:

```rust
// Así está escrito en la biblioteca estándar (no se puede usar en Rust estable):
unsafe impl<#[may_dangle] T, A: Allocator> Drop for Vec<T, A> { /* ... */ }
```

`#[may_dangle]` es una promesa (`unsafe impl`): «mi `drop` **no mira** los `T`, solo los destruye». Para que esa promesa sea segura, `Vec` debe declarar que *posee* `T`s (con un `PhantomData<T>` dentro de su puntero), de modo que el compilador siga comprobando el `drop` de cada `T`. Es el tipo de detalle que separa un contenedor sound de uno que no lo es.

**Orden de destrucción, resumido:**

| Qué | Orden |
|---|---|
| Variables locales | inverso a la declaración |
| Campos de un struct / elementos de una tupla | orden de declaración |
| Elementos de un `Vec` o array | del primero al último |
| Temporales de una sentencia | al final de la sentencia |
| `let _ = expr;` | inmediatamente (no hay enlace) |

</BajoElCapo>

## Trampa típica

<Trampa titulo="`let _ = cerrojo.lock();`">

❌ Escribir `let _ = m.lock().unwrap();` pensando que el cerrojo queda tomado hasta el final del bloque. Como `_` no enlaza, el guard se destruye **en esa misma línea**, y el `Mutex` vuelve a estar libre. Lo has visto en *Predice* con el temporal.

✅ `let _guard = m.lock().unwrap();`: el nombre que empieza por `_` evita el aviso de variable sin usar **y** mantiene vivo el valor hasta el final del ámbito.

</Trampa>
