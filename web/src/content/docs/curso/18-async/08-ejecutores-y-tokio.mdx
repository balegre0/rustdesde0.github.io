## La idea

Un **ejecutor** (*executor*) de verdad gestiona muchas **tareas** (*tasks*): futures de primer nivel, cada uno con su propio waker. Su corazón es una **cola de tareas listas**:

1. Saca una tarea de la cola y la sondea.
2. Si devuelve `Ready`, la tarea ha terminado: se suelta.
3. Si devuelve `Pending`, no se vuelve a meter en la cola **hasta que su waker la despierte**. El waker de cada tarea sabe su número y, al llamarse, lo empuja a la cola.

Cuando la cola se queda vacía pero aún hay tareas esperando E/S, entra en juego la otra mitad de un runtime: el **reactor**. Pregunta al sistema operativo «¿qué sockets o temporizadores tienen novedades?» (con `epoll` en Linux, `kqueue` en macOS y BSD, IOCP en Windows; en Tokio, a través del crate `mio`), duerme el hilo hasta que haya algo, y llama a los wakers de las tareas afectadas.

## Bajo el capó

<BajoElCapo>

**Tokio** es el runtime más usado del ecosistema (la línea 1.x es estable desde 2020; la última versión publicada es la 1.54.1, del 21 de octubre de 2026). Ofrece dos planificadores:

| Planificador | Hilos | Qué exige a las tareas |
|---|---|---|
| `current_thread` | uno: el que llama a `block_on` | basta `'static` (con `LocalSet`, ni `Send`) |
| `multi_thread` (por defecto con `#[tokio::main]`) | uno por núcleo, por defecto | `Send + 'static` |

El multihilo usa **robo de trabajo** (*work stealing*): cada hilo tiene su propia cola local y, cuando se queda sin tareas, roba la mitad de la cola de otro. Así se reparte la carga sin un cerrojo central.

Un programa Tokio típico tiene esta forma (es un **concepto**: necesita el crate `tokio`, que no está disponible en el navegador; pruébalo en el Playground o en tu proyecto con `cargo add tokio --features full`):

```rust
// Concepto: requiere el crate tokio (Playground o tu proyecto)
use tokio::time::{sleep, Duration};

#[tokio::main] // crea el runtime y hace block_on de este main
async fn main() {
    let tarea = tokio::spawn(async {      // lanza una tarea: Send + 'static
        sleep(Duration::from_millis(50)).await;
        21 * 2
    });
    let r = tarea.await.unwrap();          // JoinHandle es un future
    println!("{r}");
}
```

`#[tokio::main]` es una macro (mundo 19) que reescribe tu `main` async en un `main` normal que construye el runtime y llama a `block_on`.

**Por qué `Send`.** En el planificador multihilo, una tarea puede sondearse en un hilo, suspenderse y continuar en otro. Todo lo que viaja dentro del future (las variables vivas a través de un `.await`) tiene que poder cambiar de hilo. El compilador lo comprueba con el trait `Send` del mundo 17, y su mensaje señala la variable culpable:

<NoCompila ej="m18/rc-await" explicacion="`contador` es un `Rc`, que no es `Send`, y está vivo a través del `.await`, así que el future entero deja de ser `Send`. Fíjate en que este error no tiene código E0xxx: es un diagnóstico especial para futures. El arreglo usa `Arc`. Otra opción: soltar el `Rc` antes del `.await` (encerrándolo en un bloque)." />

**El resto del ecosistema:**
- **smol**: runtime pequeño y modular (`async-executor`, `async-io`, `futures-lite`). Es el que recomiendan los antiguos mantenedores de **async-std**, que quedó **descontinuado** con su versión 1.13.1 (21 de febrero de 2025).
- **Embassy**: async para microcontroladores, sin sistema operativo y sin asignador de memoria; los futures viven en memoria estática y el reactor son las interrupciones del hardware. Funciona en Rust estable.
- Los crates `futures` y `futures-lite` aportan utilidades independientes del runtime (`join!`, `select!`, `Stream`).

</BajoElCapo>

## Trampa típica

<Trampa titulo="Bloquear el hilo del ejecutor">

❌ Dentro de una tarea async, hacer algo que **bloquea** sin `.await`: `std::thread::sleep`, leer un archivo grande con `std::fs`, un bucle de cálculo de varios segundos.

```rust
async fn mala() {
    std::thread::sleep(std::time::Duration::from_secs(2)); // el hilo entero se para
}
```

Mientras tanto, ese hilo no sondea ninguna otra tarea: en `current_thread`, **todo** el programa se congela.

✅ Usa las versiones async (`tokio::time::sleep(...).await`, `tokio::fs`) y saca el trabajo bloqueante o pesado con `tokio::task::spawn_blocking(|| ...)`, que lo ejecuta en un grupo de hilos aparte.

</Trampa>

<Historia titulo="Un runtime que no viene de serie">
Rust decidió no incluir un runtime en la biblioteca estándar para que async sirviera igual en un servidor con 64 núcleos que en un microcontrolador de 16 KiB de RAM. El precio es que tienes que elegir uno, y que durante años convivieron varios incompatibles entre sí. Hoy el panorama está más claro: Tokio domina en servidores, smol cubre lo ligero y Embassy el embebido.
</Historia>
