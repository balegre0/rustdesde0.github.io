## La idea

Cuando `poll` devuelve `Pending`, la función **termina** (lección 2). Pero una `async fn` puede pararse a mitad, en un `.await`, y continuar después justo donde se quedó, con sus variables intactas. ¿Dónde viven esas variables mientras tanto? No en la pila, que se borró: **dentro del propio future**.

Para lograrlo, el compilador transforma el cuerpo en una **máquina de estados**: un `enum` con una variante por cada sitio donde puede estar parada la función. Cada variante guarda exactamente las variables que hacen falta para seguir desde ahí. El `poll` generado es un `match` sobre el estado actual: ejecuta hasta el próximo `.await`, cambia de variante y devuelve `Pending`; o llega al final y devuelve `Ready`.

Lo puedes escribir a mano. El ejemplo de abajo es lo que, más o menos, genera el compilador para `async fn doble(x: u32) -> u32 { Ceder(false).await; x * 2 }`.

## Pruébalo

<Ejecutar ej="m18/maquina-a-mano" />

Tres estados: `SinEmpezar` (guarda el argumento), `Esperando` (guarda `x` y el future interno) y `Terminado`. Cada `.await` del código original se convierte en «sondear el de dentro y, si dice `Pending`, devolver `Pending`».

## Bajo el capó

<BajoElCapo>

Con el compilador nightly puedes pedirle el plano exacto (`-Zprint-type-sizes`). Esta es la salida real, con rustc nightly 1.101.0, para `con_array` (allí se llama `af`):

```text
print-type-size type: `{async fn body of af()}`: 120 bytes, alignment: 8 bytes
print-type-size     discriminant: 1 bytes
print-type-size     variant `Unresumed`: 8 bytes
print-type-size         upvar `.x`: 8 bytes, offset: 0 bytes, alignment: 8 bytes
print-type-size     variant `Suspend0`: 117 bytes
print-type-size         upvar `.x`: 8 bytes, offset: 0 bytes, alignment: 8 bytes
print-type-size         local `.x`: 8 bytes
print-type-size         local `.a`: 100 bytes
print-type-size         local `.__awaitee`: 1 bytes, type: {async fn body of paso()}
print-type-size     variant `Returned`: 8 bytes
print-type-size         upvar `.x`: 8 bytes, offset: 0 bytes, alignment: 8 bytes
print-type-size     variant `Panicked`: 8 bytes
print-type-size         upvar `.x`: 8 bytes, offset: 0 bytes, alignment: 8 bytes
print-type-size     end padding: 2 bytes
```

Cómo se lee:

| Estado | Qué significa | Qué guarda |
|---|---|---|
| `Unresumed` | creado, nunca sondeado | el argumento `x` (*upvar*: capturado al crear el future) |
| `Suspend0` | parado en el primer (y único) `.await` | `x`, una copia local de `x`, el array `a` y el future interno `__awaitee` |
| `Returned` | ya devolvió `Ready` | el hueco de `x` aparece, pero ya no se usa (sondearlo otra vez provoca un pánico) |
| `Panicked` | hubo un pánico dentro | igual que `Returned` |

Las cuentas: 1 byte de discriminante + 117 del estado más grande, redondeado a múltiplo de la alineación (8) = **120**. La versión sin array mide **24**. El future de `paso()` mide **1 byte**: solo su discriminante, porque no guarda nada. En el navegador, aunque `usize` mida 4 bytes, estos tamaños salen iguales: aquí todo son `u64`, `u8` y arrays.

Nota de vocabulario: dentro del compilador estas máquinas se llaman **corrutinas** (*coroutines*); un future de `async fn` es una corrutina con una interfaz concreta.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Futures gordos sin querer">

❌ Mantener algo grande vivo a través de un `.await` aunque ya no lo necesites:

```rust
async fn primero(x: u8) -> u8 {
    let tabla = [x; 100];
    let p = tabla[0];
    paso().await;          // `tabla` sigue viva: viaja dentro del future
    p + tabla[1] - tabla[1]
}
```

Cada tarea que lances lleva esos bytes encima, y los futures anidados suman los tamaños de los de dentro. Clippy tiene una lint, `large_futures`, que avisa cuando un future pasa de cierto tamaño.

✅ Haz que lo grande muera **antes** del `.await` (enciérralo en un bloque `{ }`), o mételo en un `Box` para que dentro del future solo viaje un puntero.

</Trampa>
