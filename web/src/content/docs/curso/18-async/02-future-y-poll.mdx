## La idea

Un **future** (*futuro*) es un valor que representa un resultado que **todavía no está**. En Rust es cualquier tipo que implementa este trait de la biblioteca estándar:

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),
    Pending,
}
```

**Sondear** (*poll*) es preguntar «¿has terminado?». El future avanza todo lo que puede y responde `Poll::Ready(valor)` si acabó, o `Poll::Pending` si se ha quedado esperando algo. Nadie lo sondea solo: si no lo sondeas, no hace nada. Por eso se dice que los futures de Rust son **perezosos** (*lazy*).

De momento ignora dos detalles: `Pin<&mut Self>` (es un `&mut self` con una promesa extra; lección 7) y `Context` (lleva dentro el `Waker`; lección 3). Para sondear sin ejecutor usaremos `Waker::noop()`, un waker que no hace nada (estable desde Rust 1.85).

## Pruébalo

<Ejecutar ej="m18/future-a-mano" />

Paso a paso: `Cuenta { veces: 3 }` responde `Pending` tres veces (restando uno cada vez) y a la cuarta, `Ready`. El bucle de `main` es un **ejecutor** de juguete: sondea sin parar hasta obtener `Ready`.

`Pin::new(&mut fut)` funciona aquí porque `Cuenta` es un struct simple que se puede mover sin peligro (es `Unpin`; lo verás en la lección 7). Con el future de una `async fn` hace falta `pin!`, como en el ejemplo del principio.

## Bajo el capó

<BajoElCapo>

**Un future es solo un valor.** `Cuenta` mide 4 bytes (un `u32`). No hay hilo, ni pila propia, ni nada escondido: el «estado» de la tarea son sus campos. Cuando `poll` devuelve `Pending`, la función **termina de verdad** y su marco de pila desaparece; lo que haya que recordar para la próxima vez tiene que estar guardado en `self`. Por eso `poll` recibe `self` por referencia exclusiva: tiene que poder modificar su propio estado (aquí, `self.veces -= 1`).

**El contrato de `poll`** (documentación de `std::future::Future`):
- Si devuelve `Pending`, el future se compromete a que **alguien** llamará al `Waker` de `cx` cuando valga la pena volver a sondear. Nuestro future lo cumple con `cx.waker().wake_by_ref()` («sondéame otra vez enseguida»).
- Después de `Ready`, no se debe volver a sondear. Si lo haces, el future puede entrar en pánico, quedarse colgado o devolver cualquier cosa (pero nunca causar comportamiento indefinido: `poll` es una función segura).

**`Poll` frente a `Option`.** `Poll<T>` tiene la misma forma que `Option<T>` (dos variantes, una con dato), pero un nombre que dice lo que significa. Tiene métodos como `is_ready()`, `is_pending()` y `map`.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Devolver Pending sin avisar a nadie">

❌ Un `poll` que devuelve `Poll::Pending` y **no** guarda ni usa el waker:

```rust
fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<()> {
    Poll::Pending // nadie sabrá cuándo volver a sondear
}
```

Con un ejecutor real (que solo sondea cuando le avisan), esa tarea se queda **dormida para siempre**. No hay error ni pánico: simplemente no avanza.

✅ Antes de devolver `Pending`, o despiertas tú (`wake_by_ref()`) o entregas `cx.waker().clone()` a quien vaya a producir el dato (el sistema operativo, un temporizador, otra tarea).

</Trampa>
