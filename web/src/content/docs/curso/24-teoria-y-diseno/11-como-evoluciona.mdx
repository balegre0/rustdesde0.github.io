Rust no lo diseña una empresa ni una persona: lo diseña un proyecto abierto con cientos de colaboradores. Saber cómo se toman las decisiones te permite seguir la evolución del lenguaje y, si quieres, participar en ella.

## Quién decide

El proyecto se organiza en **equipos**: lenguaje (*lang*), biblioteca (*libs* y *libs-api*), compilador, Cargo, documentación, especificación, semántica operacional, infraestructura… Por encima está un **consejo** (*Leadership Council*) que coordina. La **Rust Foundation** es una organización aparte que da apoyo económico y legal, pero no decide el diseño.

Los cambios grandes pasan por una **RFC** (*Request for Comments*):

1. Alguien escribe un documento con la motivación, el diseño, las alternativas y los inconvenientes.
2. Se discute en público (en el repositorio `rust-lang/rfcs`).
3. El equipo responsable propone aceptarla (*final comment period*, unos 10 días) y decide.
4. Se implementa detrás de una **feature inestable**.
5. Se prueba en nightly, a veces durante años.
6. Se **estabiliza** y llega a la siguiente versión estable.

Además, cada año el proyecto define unos **objetivos** (*project goals*): las prioridades que concentran esfuerzo, como el nuevo resolutor de traits o Polonius.

## El tren y la estabilidad

- **Nightly**: cada noche, con todo lo nuevo, incluidas las features inestables (`#![feature(…)]`).
- **Beta**: lo que será la próxima estable.
- **Stable**: cada **6 semanas**. Es la que usas.

La **promesa de estabilidad**: el código que compila en una versión estable seguirá compilando en todas las siguientes. Hay excepciones muy acotadas (arreglos de seguridad o de *soundness*, como el #25860), y se comprueban compilando **todo crates.io** con la versión nueva antes de publicarla (*crater*).

Los cambios que romperían código se hacen con una **edición** (2015, 2018, 2021, 2024): cada paquete elige la suya en `Cargo.toml`, `cargo fix --edition` migra casi todo de forma automática, y paquetes de ediciones distintas se usan entre sí sin problema.

## Contribuir

Contribuir a Rust no exige ser experto. Por orden de dificultad:

1. **Documentación**: arreglar o mejorar la de la biblioteca estándar (está en el propio código, con `///`).
2. **Diagnósticos**: mejorar un mensaje de error confuso. Los mensajes de `rustc` son buenos porque mucha gente los ha pulido así.
3. **Incidencias marcadas** como *E-easy* o *E-mentor* en `rust-lang/rust`.
4. **Clippy**: añadir o mejorar un aviso.
5. **Verificación** de la biblioteca estándar (lección 9).

El punto de partida es la **rustc-dev-guide** (la guía oficial de desarrollo del compilador). Para compilar el compilador:

```powershell
git clone https://github.com/rust-lang/rust
cd rust
./x setup        # elige el perfil «compiler»
./x build        # compila rustc (la primera vez tarda bastante)
./x test tests/ui --bless   # pruebas de la interfaz de errores
```

## Bajo el capó

<BajoElCapo>

**Bootstrapping.** `rustc` está escrito en Rust, así que para compilarlo hace falta un `rustc`. El sistema `x` descarga el compilador beta (la *etapa 0*), compila con él el compilador nuevo (*etapa 1*) y, opcionalmente, vuelve a compilarlo con ese (*etapa 2*). Lo viste en el mundo 21.

**Las pruebas de interfaz** (`tests/ui`) son programas pequeños junto con el mensaje de error exacto que deben producir. Si mejoras un mensaje, `--bless` actualiza los archivos esperados y la revisión de tu cambio consiste, sobre todo, en leer esa diferencia.

</BajoElCapo>
