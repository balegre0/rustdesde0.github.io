## La idea

Un **combinador** es un método que transforma un `Result` (u `Option`) en otro sin que tengas que escribir el `match`. Los esenciales:

| Método | Sobre | Hace |
|---|---|---|
| `map(f)` | `Ok(v)` | `Ok(f(v))`; un `Err` pasa intacto |
| `map_err(f)` | `Err(e)` | `Err(f(e))`; un `Ok` pasa intacto |
| `and_then(f)` | `Ok(v)` | `f(v)`, donde `f` **devuelve otro `Result`** |
| `ok_or(e)` | `Option` | `Some(v)` → `Ok(v)`; `None` → `Err(e)` |
| `ok()` | `Result` | `Ok(v)` → `Some(v)`; `Err` → `None` |
| `unwrap_or_else(f)` | `Err(e)` | calcula un valor de reserva a partir del error |

Las `|n| n * 2` que ves son **closures** (funciones anónimas): `|parámetros| cuerpo`. Las estudiarás en el mundo 14; por ahora léelas como «dado `n`, devuelve `n * 2`».

Y una joya para listas: si tienes un iterador de `Result`, `collect::<Result<Vec<_>, _>>()` te da **o todos los valores, o el primer error**. Es la respuesta a una pregunta muy común: «¿cómo paro un `map` en cuanto algo falla?».

## Bajo el capó

<BajoElCapo>

Cada combinador es un `match` corto dentro de la biblioteca estándar. `map`, por ejemplo, es exactamente:

```rust
match self {
    Ok(t) => Ok(op(t)),
    Err(e) => Err(e),
}
```

Como el compilador sustituye la llamada por su cuerpo (*inlining*) y la closure también, una cadena `parse().map(…).map_err(…)` produce el mismo código máquina que los `match` escritos a mano. Elige entre `?`, `match` y combinadores por **claridad**, no por velocidad.

`collect` hacia `Result<Vec<T>, E>` funciona porque `Result` implementa el trait `FromIterator`: va pidiendo elementos y, al primer `Err`, deja de consumir el iterador. Los elementos que quedaban detrás ni se calculan.

</BajoElCapo>
