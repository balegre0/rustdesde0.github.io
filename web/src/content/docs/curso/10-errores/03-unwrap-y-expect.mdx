## La idea

`unwrap()` dice: «sé que esto es `Ok` (o `Some`); dame el valor. Si me equivoco, pánico». `expect("…")` hace lo mismo, pero el mensaje del pánico incluye **tu explicación**. Cuando falle, sabrás qué suponías:

```text
la configuración debe traer un número: ParseIntError { kind: InvalidDigit }
```

frente a

```text
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
```

Son herramientas legítimas en **tres** situaciones: pruebas (mundo 16), prototipos que aún no tratan errores, y valores que **no pueden fallar** por cómo está escrito el programa (un número escrito a mano en el código). Fuera de eso, convierten un error normal en un pánico. Si hay un valor razonable de reserva, usa `unwrap_or`, `unwrap_or_default` o `unwrap_or_else`; si no, propaga el error con `?` (lección 4).

## Bajo el capó

<BajoElCapo>

`unwrap` es un `match` con un pánico en el brazo de error. Simplificando, la biblioteca estándar hace:

```rust
match self {
    Ok(t) => t,
    Err(e) => unwrap_failed("called `Result::unwrap()` on an `Err` value", &e),
}
```

Por eso `unwrap` sobre un `Result<T, E>` **exige** que `E` se pueda imprimir con `{:?}` (que implemente `Debug`): necesita mostrar el error en el mensaje. Y la ubicación del pánico (`archivo:línea:columna`) apunta a **tu** llamada, no al interior de la biblioteca, gracias al atributo `#[track_caller]`, que le pasa a la función la posición de quien la llamó.

`unwrap_or(x)` evalúa `x` **siempre**, aunque no se use; `unwrap_or_else(|| …)` solo lo calcula si hace falta. Si el valor de reserva es caro de construir, usa la versión `_else`.

</BajoElCapo>
