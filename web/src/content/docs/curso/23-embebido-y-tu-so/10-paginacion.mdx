Las direcciones que has visto en todo el curso (`0xfffc4`, `0x7ffd…`) no son las de los chips de RAM: son **virtuales**. Quien las traduce es la CPU, siguiendo unas tablas que prepara el núcleo. Aquí ves cómo.

## La idea

La memoria se divide en **páginas** de 4 KiB. El núcleo mantiene unas **tablas de páginas** que dicen, para cada página virtual, en qué **marco** de memoria física está (y con qué permisos: escritura, ejecución, acceso desde programas de usuario).

En x86_64 la tabla tiene **cuatro niveles**. Una dirección virtual de 48 bits se parte así:

```text
 47      39 38      30 29      21 20      12 11          0
┌─────────┬──────────┬──────────┬──────────┬─────────────┐
│ P4 (9)  │  P3 (9)  │  P2 (9)  │  P1 (9)  │ desplaz.(12)│
└─────────┴──────────┴──────────┴──────────┴─────────────┘
```

La CPU empieza en la tabla P4 (su dirección está en el registro `CR3`), usa el primer índice para encontrar la tabla P3, y así hasta la entrada de P1, que da el marco físico. El desplazamiento se suma al final. Cada tabla tiene 2⁹ = 512 entradas de 8 bytes: justo una página.

## Pruébalo

<Ejecutar ej="m23/paginacion" />

`0x7fff_ffff_f000`, la última página de la mitad baja (donde suele estar la pila de un programa), usa la última entrada (511) de los tres niveles inferiores.

## Bajo el capó

<BajoElCapo>

**La TLB.** Recorrer cuatro tablas en cada acceso sería lentísimo. La CPU guarda las traducciones recientes en una caché, la **TLB**. Cuando el núcleo cambia una tabla, tiene que invalidar la entrada correspondiente (`invlpg`), o la CPU seguiría usando la traducción vieja.

**Qué es un fallo de página.** Si una entrada no está presente o no tiene permiso, la CPU lanza la excepción **page fault** (lección 9) con la dirección culpable en el registro `CR2`. Un sistema operativo de verdad la usa para cargar páginas bajo demanda; tu núcleo, por ahora, solo para mostrar el error. Desde Rust, desreferenciar un puntero a memoria no mapeada en un programa normal acaba precisamente aquí: el sistema operativo recibe el fallo de página y mata el proceso con *segmentation fault* o *access violation*.

**Cómo accede el núcleo a las tablas.** Las tablas guardan direcciones **físicas**, pero el núcleo también trabaja con direcciones virtuales. blog_os explica varias soluciones (mapear toda la memoria física en un desplazamiento fijo, tablas recursivas) y usa la primera, que el cargador de arranque prepara.
