Tus pruebas comprueban **tu** código haciendo lo que esperas. Quedan dos huecos: el código de **otros** que usas (tus dependencias) y los errores que no se ven en la salida (el comportamiento indefinido en bloques `unsafe`). Vas a conocer las herramientas para los dos.

## Predice

```rust
fn main() {
    let v = vec![10, 20, 30];
    let p = v.as_ptr();
    // SAFETY: ninguna. Leemos una posición que no existe (índice 3).
    let x = unsafe { *p.add(3) };
    println!("{x}");
}
```

## La idea

**Dependencias.** Un proyecto real usa crates de crates.io, y esos crates usan otros. Cualquiera puede tener una vulnerabilidad descubierta después de que lo añadieras. La comunidad mantiene una base de datos pública, **RustSec**, con avisos de seguridad (*advisories*) sobre crates concretos y las versiones afectadas. Dos herramientas la usan:

- **`cargo audit`** lee tu `Cargo.lock` (las versiones **exactas** que estás usando) y te dice cuáles tienen avisos.
- **`cargo deny check`** hace eso y más: rechaza licencias que no quieres, crates repetidos en varias versiones, crates prohibidos o dependencias que vienen de fuentes no autorizadas. Se configura en un archivo `deny.toml`.

Las dos se instalan aparte (`cargo install cargo-audit`, `cargo install cargo-deny`) y necesitan descargar la base de datos. **No están instaladas en el entorno de este curso, así que no te mostramos su salida.** Lo que sí puedes ver en cualquier sitio es tu árbol de dependencias, con `cargo tree`. Esta es la salida real de un proyecto `app` que depende de las bibliotecas `notas` y `clave` de este mundo (rutas acortadas):

```text title="cargo tree (salida real)"
app v0.1.0 (…\app)
├── clave v0.1.0 (…\clave)
└── notas v0.1.0 (…\notas)
```

`cargo tree -i notas` invierte el árbol: muestra **quién** depende de `notas`. Es lo que necesitas cuando `cargo audit` te avisa de un crate que no recuerdas haber añadido.

**Comportamiento indefinido.** En el mundo 20 verás `unsafe` a fondo. Por ahora basta una idea: dentro de un bloque `unsafe`, tú garantizas ciertas reglas (punteros válidos, memoria inicializada, nada de préstamos exclusivos duplicados…) y el compilador deja de comprobarlas. Si te equivocas, el programa tiene **UB**: puede hacer cualquier cosa, incluso parecer correcto. **Miri** es la herramienta que lo detecta.

## Pruébalo

Primero, la buena noticia: en Rust **seguro** este problema no existe. Leer fuera de un vector, o te devuelve `None`, o entra en pánico de forma ruidosa. Nunca lee memoria ajena:

<Ejecutar ej="m16/get-seguro" />

Miri sirve para cuando **sí** usas `unsafe` (o una dependencia tuya lo usa). Se instala y se usa así (necesita la toolchain nightly):

```text
rustup +nightly component add miri
cargo +nightly miri run      # ejecuta main bajo Miri
cargo +nightly miri test     # ejecuta tus pruebas bajo Miri
```

Ante el programa del principio, Miri detiene la ejecución en la línea del `*p.add(3)` con un error de **UB** que explica que se ha accedido a memoria fuera de la asignación del vector. En el entorno de este curso Miri no puede preparar su biblioteca estándar (para eso necesita también el enlazador), así que **no te mostramos su salida aquí**. La forma más fácil de verlo tú: pega el programa en el **Rust Playground** (play.rust-lang.org) y elige *Tools → Miri*.

## Bajo el capó

<BajoElCapo>

Recuerda el viaje de tu código por el compilador: texto → árbol de sintaxis → … → **MIR** (*Mid-level Intermediate Representation*, una versión simplificada de tu programa que usa el borrow checker) → LLVM → código máquina. **Miri es un intérprete de MIR**: en vez de convertir tu programa en instrucciones del procesador, lo ejecuta paso a paso dentro de una máquina virtual que **lleva la cuenta de todo**:

- Cada asignación de memoria (cada `Box`, cada `Vec`) con su tamaño exacto, para detectar accesos fuera de límites o a memoria ya liberada (**uso tras liberar**).
- Qué bytes están inicializados, para detectar lecturas de memoria sin inicializar.
- De qué asignación «procede» cada puntero (su *provenance*), para detectar punteros que se salen de la suya aunque la dirección caiga en otra válida.
- Los préstamos vivos de cada posición, con un modelo llamado **Stacked Borrows** (o **Tree Borrows**, con `MIRIFLAGS=-Zmiri-tree-borrows`), para detectar un `&mut` usado mientras otro préstamo al mismo dato sigue vivo: el **aliasing con mutación** que el borrow checker impide en Rust seguro.

Como interpreta, Miri es **muchísimo más lento** que el programa compilado: se usa con pruebas pequeñas, no con el programa entero. Y solo detecta UB en los caminos que **se ejecutan**: si tu prueba no pasa por la línea problemática, Miri no la ve. Por eso se combina con buenas pruebas e incluso con fuzzing.

Detecta también **fugas de memoria** (memoria reservada que nunca se libera) al final del programa y te avisa. Una fuga **no** es UB en Rust: `std::mem::forget` y `Box::leak` son funciones seguras. Es un error de recursos, no de seguridad de memoria.

</BajoElCapo>

## Trampa típica

<Trampa titulo="«Mis pruebas pasan, así que mi unsafe está bien»">

❌ Una prueba llama a una función con `unsafe` dentro, comprueba el resultado y pasa. Pero el resultado puede ser correcto **por casualidad**: la memoria que leíste fuera de límites resultaba tener el valor esperado, o el optimizador aún no ha decidido aprovechar tu UB. Con otra versión del compilador, otro procesador u otra opción de optimización, deja de funcionar.

✅ Todo crate con `unsafe` debería ejecutar sus pruebas también bajo Miri (`cargo +nightly miri test`), a menudo en la integración continua. Y cada bloque `unsafe` debería llevar un comentario `// SAFETY:` que explique por qué se cumplen las reglas: si no puedes escribirlo, probablemente no se cumplen.

</Trampa>
