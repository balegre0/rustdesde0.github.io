La documentación miente con el tiempo: cambias una función y el ejemplo del comentario se queda viejo. En Rust eso tiene arreglo: los ejemplos de la documentación **son pruebas**.

## La idea

Un **comentario de documentación** (*doc comment*) empieza con tres barras, `///`, y se escribe en Markdown justo encima de lo que documenta. Si dentro pones un bloque de código, ese bloque es un **doctest**:

````rust title="src/lib.rs"
/// Calcula la media de una lista de notas.
///
/// Devuelve `None` si la lista está vacía.
///
/// ```
/// use notas::media;
///
/// assert_eq!(media(&[6.0, 8.0]), Some(7.0));
/// assert_eq!(media(&[]), None);
/// ```
pub fn media(notas: &[f64]) -> Option<f64> {
    // …
}
````

`cargo test` lo trata como un programa pequeño **desde fuera** de tu crate, igual que una prueba de integración: por eso necesita `use notas::media;`. Cumple dos funciones a la vez: quien lee la documentación ve cómo se usa la función, y tú tienes la garantía de que ese uso **funciona hoy**.

Después de los tres acentos graves de apertura puedes poner atributos que cambian lo que se comprueba:

| Bloque | Qué hace `cargo test` |
|---|---|
| `` ``` `` | compila y ejecuta; falla si no compila o entra en pánico |
| `` ```should_panic `` | compila y ejecuta; falla si **no** entra en pánico |
| `` ```compile_fail `` | intenta compilar; falla si **sí** compila |
| `` ```no_run `` | solo compila (útil si se colgaría, o usa la red) |
| `` ```ignore `` | nada; sale como `ignored` |
| `` ```text `` | no es Rust: nunca se trata como prueba |

## Pruébalo

Una función documentada con un ejemplo de cada tipo:

````rust title="src/lib.rs"
/// Divide `a` entre `b`.
///
/// ```
/// # use calculo::divide;
/// assert_eq!(divide(10, 2), 5);
/// ```
///
/// Dividir entre cero es un pánico:
///
/// ```should_panic
/// calculo::divide(1, 0);
/// ```
///
/// El resultado es un `i32`; guardarlo en un `u32` no compila:
///
/// ```compile_fail
/// let x: u32 = calculo::divide(1, 1);
/// ```
///
/// ```no_run
/// // Compila pero no se ejecuta: imagina que esto tardara una hora.
/// loop { calculo::divide(1, 1); }
/// ```
///
/// ```ignore
/// esto ni siquiera es Rust válido
/// ```
pub fn divide(a: i32, b: i32) -> i32 {
    a / b
}
````

`cargo test --doc` ejecuta solo los doctests. Salida real (quitando la línea de aviso del entorno wasm donde se ejecutó):

```text title="cargo test --doc (salida real)"
   Doc-tests calculo

running 3 tests
test src\lib.rs - divide (line 12) - should panic ... ignored
test src\lib.rs - divide (line 22) - compile ... ok
test src\lib.rs - divide (line 5) ... ok

test result: ok. 2 passed; 0 failed; 1 ignored; 0 measured; 0 filtered out; finished in 0.00s


running 2 tests
test src\lib.rs - divide (line 27) ... ignored
test src\lib.rs - divide (line 18) - compile fail ... ok

test result: ok. 1 passed; 0 failed; 1 ignored; 0 measured; 0 filtered out; finished in 0.07s

all doctests ran in 0.60s; merged doctests compilation took 0.46s
```

Cada doctest se nombra por **archivo, elemento y línea**: `src\lib.rs - divide (line 5)`. El `no_run` aparece como `- compile ... ok`: se compiló, no se ejecutó. El `should_panic` sale `ignored` por la misma razón que viste en la lección 2: este entorno wasm aborta en los pánicos y no puede recogerlos. En tu PC se ejecuta y pasa.

La línea `# use calculo::divide;` se compila, pero **no se ve** en la documentación generada. Es la forma de esconder preparativos que distraerían del ejemplo.

## Bajo el capó

<BajoElCapo>

`cargo test --doc` llama a **rustdoc**, no a `rustc` directamente. Para cada bloque:

1. Extrae el código y quita las almohadillas de las líneas ocultas.
2. Si no hay un `fn main`, **lo envuelve** en uno: tu ejemplo pasa a ser el cuerpo de `main`. Por eso en un doctest puedes escribir sentencias sueltas.
3. Lo compila como un crate externo que depende del tuyo.

Fíjate en que hubo **dos tandas** en la salida y en la última línea: `merged doctests compilation`. Desde la **edición 2024**, rustdoc junta en **un solo programa** todos los doctests que puede (los de la primera tanda) y lo compila de una vez, que es mucho más rápido que compilar un programa por ejemplo. Los que no se pueden juntar —los `compile_fail`, porque cada uno *debe* fallar por separado, y los que lo piden con el atributo `standalone_crate`— se compilan aparte en la segunda tanda.

Un doctest que devuelve error también puede usar `?`: si terminas el ejemplo con `Ok::<(), String>(())` (con la línea oculta si quieres), rustdoc lo envuelve en un `main` que devuelve `Result`.

</BajoElCapo>

## Trampa típica

<Trampa titulo="compile_fail que «pasa» por el motivo equivocado">

Un `compile_fail` solo comprueba que el código **no compila**, no **por qué**. Este ejemplo quiere enseñar el error de usar una `String` después de moverla. Compilado como programa da justo ese error:

<NoCompila ej="m16/doc-compile-fail" explicacion="E0382: `nombre` se movió a `otro` y después se intenta usar. Es lo que el doctest quería demostrar." />

❌ Pero si dentro del doctest te equivocas al escribir (por ejemplo `Strin::from`), también falla al compilar… y el doctest **pasa igual**, sin demostrar nada.

✅ Puedes fijar el **código de error** esperado: `` ```compile_fail,E0382 ``. Así rustdoc comprueba que el fallo sea el que buscabas (esta comprobación de código solo se aplica en la toolchain nightly; en estable el doctest pasa con cualquier error, así que revisa tus `compile_fail` a mano de vez en cuando).

</Trampa>
