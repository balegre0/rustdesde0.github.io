## La idea

Un **benchmark** es una prueba que en vez de comprobar *qué* da tu código, mide *cuánto tarda*. Hay tres enemigos que debes conocer:

1. **El perfil equivocado.** En debug no hay optimización: puedes llegar a medir un programa decenas de veces más lento que el real. Se mide **siempre en release**.
2. **El optimizador.** En release, el compilador es muy listo: si ve que un resultado no se usa, borra el cálculo; si conoce los datos, lo hace él al compilar. Tu medida dice «0 segundos» y es mentira.
3. **El ruido.** Otros programas, la temperatura del procesador, la caché… Una sola medida no significa nada. Hay que repetir y mirar estadísticas.

Contra el segundo enemigo, la biblioteca estándar tiene **`std::hint::black_box`** (estable desde Rust 1.66): una función que devuelve su argumento sin cambiarlo, pero que el optimizador trata como una «caja negra». No sabe qué entra ni qué se hace con lo que sale, así que no puede precalcular ni borrar nada.

## Pruébalo

Un cronómetro casero con `Instant` que compara dos formas de sumar de 0 a n−1: un bucle y la fórmula de Gauss. Fíjate en el paso 3: **antes de comparar velocidades, comprueba que las dos versiones dan lo mismo**. Una función rapidísima que da un resultado incorrecto no vale nada.

<Ejecutar ej="m16/cronometro" />

Los tiempos cambian en cada ejecución y dependen de la máquina; aquí se ejecuta en WebAssembly dentro de tu navegador, que no es el entorno de tu programa final. Lo que importa es la **proporción**: la fórmula hace tres operaciones y el bucle, un millón de vueltas. Ningún truco de compilador cambia eso… salvo uno que vas a ver ahora.

## Bajo el capó

<BajoElCapo>

Estas dos funciones, compiladas con `rustc -O --emit=asm` para x86-64 (Windows), sin `black_box`:

```rust
#[unsafe(no_mangle)]
pub fn suma_bucle(n: u64) -> u64 {
    let mut s = 0;
    let mut i = 0;
    while i < n {
        s += i;
        i += 1;
    }
    s
}

#[unsafe(no_mangle)]
pub fn diez_veces() -> u64 {
    let mut t = 0;
    for _ in 0..10 {
        t += suma_bucle(1000);
    }
    t
}
```

Producen este ensamblador (real, quitando las directivas):

```text title="ensamblador real (x86-64, -O)"
diez_veces:
	mov	eax, 4995000
	ret

suma_bucle:
	test	rcx, rcx
	je	.LBB1_1
	lea	rax, [rcx - 1]
	lea	rdx, [rcx - 2]
	mul	rdx
	shld	rdx, rax, 63
	lea	rax, [rcx + rdx]
	dec	rax
	ret
.LBB1_1:
	xor	eax, eax
	ret
```

Dos sorpresas. **`suma_bucle` ya no tiene bucle**: LLVM (el optimizador que usa Rust) reconoció el patrón «sumar de 0 a n−1» y lo sustituyó por una fórmula con una multiplicación (`mul`) y un desplazamiento (`shld … 63`, que divide entre 2). Y **`diez_veces` es una sola instrucción**: como los datos (`1000`, diez veces) se conocen al compilar, calculó `10 × 499 500 = 4 995 000` él mismo. Si cronometraras `diez_veces`, medirías el tiempo de devolver un número.

Por eso el ejemplo de arriba envuelve `n` en `black_box(n)` (el optimizador ya no sabe cuánto vale) y el resultado en `black_box(…)` (no sabe si se usa). Y aun así, fíjate: en tu PC con `--release`, el «bucle» de `suma_bucle` podría acabar siendo también una fórmula. Medir te dice **qué pasa de verdad**, que no siempre es lo que el código fuente parece decir.

</BajoElCapo>

## Herramientas de verdad: criterion y divan

Para medir en serio se usan crates del ecosistema. Los dos más conocidos son **criterion** y **divan**. Se descargan de crates.io, así que **no están instalados en el entorno de este curso: el código de abajo no se ha compilado aquí** y no te enseñamos su salida. Sirve para que reconozcas la forma.

Con criterion, los benchmarks van en `benches/`, y en `Cargo.toml` se desactiva el arnés por defecto:

```toml title="Cargo.toml (esquema)"
[dev-dependencies]
criterion = "…"   # la versión que indique crates.io

[[bench]]
name = "sumas"
harness = false
```

```rust title="benches/sumas.rs (esquema, no compilado aquí)"
use criterion::{criterion_group, criterion_main, Criterion};
use std::hint::black_box;

fn medir(c: &mut Criterion) {
    c.bench_function("suma_bucle 1e6", |b| b.iter(|| mi_crate::suma_bucle(black_box(1_000_000))));
}

criterion_group!(benches, medir);
criterion_main!(benches);
```

Se ejecuta con `cargo bench`, que compila en un perfil optimizado. Lo que aportan sobre tu cronómetro casero: un **calentamiento** antes de medir (para que la caché y el procesador estén en régimen normal), **muchas repeticiones** elegidas automáticamente, **estadísticas** (media, intervalo de confianza, valores atípicos) y **comparación con la ejecución anterior**, que te avisa si un cambio ha empeorado el tiempo. divan ofrece lo mismo con una sintaxis más corta, un atributo `#[divan::bench]` encima de cada función.

(Existe también un atributo `#[bench]` en la propia biblioteca de pruebas, pero solo funciona en la toolchain nightly.)

## Trampa típica

<Trampa titulo="Medir en debug">

❌ `cargo run` y cronometrar. Debug no optimiza y comprueba cada suma por si desborda: mides algo que tu usuario nunca ejecutará, y puedes «optimizar» lo que en release ya era rápido.

✅ `cargo run --release` para cronómetros caseros, `cargo bench` para benchmarks con criterion o divan. Y antes de comparar dos versiones, comprueba con un `assert_eq!` que hacen lo mismo.

</Trampa>
