## La idea

Cuando una prueba falla, `cargo test` te da tres pistas: **qué prueba** falló (su nombre completo), **dónde** (archivo, línea y columna del `assert`) y **por qué** (el mensaje y, con `assert_eq!`, los dos valores). Un buen mensaje ahorra minutos: escribe en él lo que *esperabas* y los datos que usaste.

Además de comprobar valores, a menudo quieres comprobar que algo **falla bien**. Rust te da tres herramientas:

- **`#[should_panic]`**: la prueba pasa solo si entra en pánico. Con `expected = "texto"` exiges además que el mensaje contenga ese texto.
- **Pruebas que devuelven `Result<(), E>`**: así puedes usar `?` dentro. Si sale un `Err`, la prueba falla y se muestra el error.
- **`#[ignore]`**: aparta una prueba (por ejemplo, una lenta). No se ejecuta salvo que lo pidas con `cargo test -- --ignored`.

## Pruébalo

Estas son pruebas reales de una pequeña biblioteca de notas. Cada una enseña una herramienta:

```rust title="src/lib.rs (fragmento)"
pub fn parsear(texto: &str) -> Result<f64, String> { /* … */ }
pub fn nota_en(notas: &[f64], i: usize) -> f64 { notas[i] }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn cinco_aprueba() {
        assert!(aprobado(5.0));
        assert!(!aprobado(4.9), "4.9 no debería aprobar");
    }

    // 1. Una prueba que devuelve Result: puede usar `?`.
    #[test]
    fn parsear_bien() -> Result<(), String> {
        let n = parsear(" 7.5 ")?;
        assert_eq!(n, 7.5);
        Ok(())
    }

    // 2. Debe entrar en pánico, y con ese mensaje.
    #[test]
    #[should_panic(expected = "index out of bounds")]
    fn nota_fuera_de_rango() {
        nota_en(&[1.0], 3);
    }

    // 3. Lenta: solo con `cargo test -- --ignored`.
    #[test]
    #[ignore = "lento: recorre un millón de notas"]
    fn muchas_notas() {
        let v = vec![5.0; 1_000_000];
        assert_eq!(media(&v), Some(5.0));
    }
}
```

Y así se ve `cargo test -- --ignored`, que ejecuta **solo** las ignoradas:

```text title="cargo test -- --ignored (salida real, recortada)"
running 1 test
test tests::muchas_notas ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 5 filtered out; finished in 0.02s
```

Fíjate en el `--` del medio: lo que va **antes** es para Cargo; lo que va **después**, para el programa de pruebas.

Ahora, un fallo de verdad. Esta función tiene un error y la prueba lo caza:

```rust
pub fn doble(x: i32) -> i32 {
    x * 3 // ¡error! debería ser x * 2
}

#[test]
fn doble_de_dos() {
    assert_eq!(doble(2), 4);
}
```

El mensaje que produce el `assert_eq!` (salida real):

```text
assertion `left == right` failed
  left: 6
 right: 4
```

En tu PC, `cargo test` además lo envuelve en un **informe de fallos**. Para ver su forma exacta, aquí tienes uno real de una prueba que falla devolviendo `Err` (como `parsear_bien`, pero con el texto `"abc"`):

```text title="informe real de una prueba fallida"
running 1 test
test leer_numero ... FAILED

failures:

---- leer_numero stdout ----
Error: ParseIntError { kind: InvalidDigit }


failures:
    leer_numero

test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Tres partes: la línea `FAILED`, una sección por cada prueba fallida con lo que imprimió (aquí, el error con `Debug`; con un `assert_eq!` fallido, el mensaje `left`/`right` de arriba junto con el archivo y la línea) y la lista de los nombres que fallaron. El programa termina con un código de error (101), que es lo que usan los servidores de integración continua para saber que algo se ha roto.

Un primo de `assert!`: **`debug_assert!`**, que solo se comprueba en el perfil debug. Sirve para comprobaciones caras que quieres durante el desarrollo pero no en el programa final. Este ejemplo muestra los dos perfiles:

## Bajo el capó

<BajoElCapo>

¿Cómo puede el arnés **seguir ejecutando pruebas** después de que una entre en pánico? Porque en tu PC, por defecto, un pánico **desenrolla la pila** (*unwinding*): va destruyendo los marcos de pila de las funciones, ejecutando los `Drop` de cada variable, hasta que alguien lo recoge. El arnés ejecuta cada prueba en su propio hilo y recoge el pánico al final de ese hilo. Para él, «pánico recogido» = `FAILED`, y pasa a la siguiente.

Esto tiene una consecuencia que verás en la plataforma de este curso. WebAssembly se compila con `panic = "abort"`: un pánico **detiene el programa entero** en el acto, sin desenrollar. Por eso, en wasm, el arnés marca las pruebas `#[should_panic]` como `ignored` (no tiene forma de recogerlas) y una prueba que falla corta todas las demás. Esta es la línea real de la salida en wasm:

```text
test tests::nota_fuera_de_rango - should panic ... ignored
```

En tu PC, con el enlazador instalado, esa misma prueba se ejecuta y aparece como `ok`. Lo mismo pasa si configuras `panic = "abort"` en tu `Cargo.toml`: las pruebas que dependen de recoger pánicos dejan de tener sentido.

`#[should_panic(expected = "…")]` compara con el **mensaje** del pánico como subcadena. El mensaje de un índice fuera de rango empieza por `index out of bounds`, por eso basta con ese trozo.

</BajoElCapo>

## Trampa típica

<Trampa titulo="should_panic sin expected acepta cualquier pánico">

❌ Esta prueba quiere comprobar que repartir entre cero personas entra en pánico. Pero tiene un despiste que provoca **otro** pánico… y la prueba pasa igual:

```rust
fn reparto(total: u32, personas: u32) -> u32 {
    total / personas
}

#[test]
#[should_panic]
fn repartir_entre_nadie() {
    let grupos: Vec<u32> = vec![];
    reparto(100, grupos[0]); // grupos está vacío: pánico por el índice, no por el cero
}
```

El pánico real aquí es `index out of bounds: the len is 0 but the index is 0`: la división ni se llega a hacer. La prueba «pasa» sin probar nada.

✅ Con `expected`, solo pasa si el pánico es **el que buscabas** (el mensaje real de dividir un entero entre cero es `attempt to divide by zero`):

```rust
#[test]
#[should_panic(expected = "attempt to divide by zero")]
fn repartir_entre_nadie() {
    reparto(100, 0);
}
```

</Trampa>
