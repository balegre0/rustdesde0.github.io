## La idea

rustdoc lee tus comentarios de documentación y genera **HTML**: una página por elemento público, con buscador, enlaces entre tipos y el código fuente. Lo lanzas con `cargo doc` (y `cargo doc --open` para abrirla en el navegador). La documentación de la biblioteca estándar, la de cualquier crate en docs.rs y la tuya salen de la misma herramienta.

Hay dos tipos de comentario. `///` documenta lo que viene **detrás**. `//!` documenta lo que lo **contiene** (el crate o el módulo). Dentro escribes Markdown, y la comunidad sigue unas **secciones de costumbre** que cualquiera que use Rust sabe leer:

| Sección | Cuándo |
|---|---|
| `# Ejemplos` | casi siempre: un doctest con el uso típico |
| `# Errores` | si devuelve `Result`: qué casos dan `Err` |
| `# Pánicos` | si puede entrar en pánico: en qué casos |
| `# Safety` | si es `unsafe fn`: lo que debe garantizar quien la llama (mundo 20) |

La primera frase es la más importante: rustdoc la usa como **resumen** en las listas. Que sea corta y diga qué hace.

## Pruébalo

Un pequeño conversor documentado como una biblioteca de verdad. El `main` ejecuta a mano lo que prometen sus ejemplos y su sección de errores:

<Ejecutar ej="m16/documentado" />

Mira el comentario de `a_celsius`: ``[`a_fahrenheit`]`` es un **enlace interno** (*intra-doc link*). rustdoc busca ese nombre igual que lo haría el compilador y lo convierte en un enlace a su página.

Así responde `cargo doc` cuando algo va mal. Este es un proyecto con `#![warn(missing_docs)]`, una función sin documentar y un enlace a una función que no existe (salida real, con la ruta acortada):

```text title="cargo doc --no-deps (salida real)"

El primer aviso lo da el compilador (`missing_docs`): solo se queja de lo **público**, que es lo que verán los demás. El segundo, rustdoc: el enlace a `a_kelvin` no lleva a ninguna parte. `cargo doc` no necesita el enlazador, así que funciona aunque no tengas las Build Tools.

## Bajo el capó

<BajoElCapo>

Un comentario de documentación es **azúcar sintáctico** de un atributo: `/// Hola` equivale a `#[doc = " Hola"]` (fíjate en el espacio inicial, que se conserva), y `//! Hola` a `#![doc = " Hola"]`. Lo puedes comprobar: este archivo, con `#![warn(missing_docs)]`, solo avisa por `b`, porque `a_f` está documentada con el atributo escrito a mano:

```rust
#![warn(missing_docs)]
#![doc = " Conversión."]

#[doc = " Pasa grados."]
pub fn a_f(c: f64) -> f64 { c }
pub fn b(c: f64) -> f64 { c }
```

Por eso la documentación viaja con el código: forma parte del árbol que lee el compilador, igual que `#[derive]` o `#[test]`. rustdoc usa la misma parte inicial del compilador (lectura, expansión de macros, resolución de nombres y tipos), pero en vez de generar código máquina escribe HTML.

Lo que deja en `target/doc/` (real, del proyecto anterior): una carpeta por crate (`docs1/` con `index.html`, `fn.a_fahrenheit.html`, `fn.a_celsius.html`, `all.html`), un índice de búsqueda (`search.index`) que el buscador consulta en tu navegador sin servidor, y una copia del código fuente (`src/`) para el botón «Source». Cada página de función se llama `fn.<nombre>.html`; las de structs, `struct.<nombre>.html`.

Opciones útiles: `cargo doc --no-deps` documenta solo tu crate (sin tus dependencias), y `cargo doc --document-private-items` incluye también lo privado, útil para el equipo que mantiene el código.

</BajoElCapo>

## Trampa típica

<Trampa titulo="Documentar el cómo en vez del qué">

❌ Repite el código con palabras. Quien usa tu función no necesita saber cómo está hecha por dentro:

```rust
/// Recorre la lista con un iterador, suma todo con sum()
/// y divide entre len() convertido a f64.
pub fn media(notas: &[f64]) -> Option<f64> { /* … */ }
```

✅ Dice **qué** hace, **cuándo falla** y **cómo se usa**:

````rust
/// Calcula la media de una lista de notas.
///
/// Devuelve `None` si la lista está vacía.
///
/// # Ejemplos
///
/// ```
/// assert_eq!(notas::media(&[6.0, 8.0]), Some(7.0));
/// ```
pub fn media(notas: &[f64]) -> Option<f64> { /* … */ }
````

</Trampa>
